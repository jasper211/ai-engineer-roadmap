# WPS 云文档 → 服务器镜像 · 交接说明

> 建档 2026-09-21。技术实现方（Jasper）交付后不再参与日常运行，本文档是接手方唯一需要看的东西。

---

## 一、这套东西在做什么

WPS 企业云盘上 11 个库的全部文件，每天凌晨 2 点自动复制一份到公司服务器，
再由 Syncthing 分发到管理层各自的电脑上。

```
 WPS 云盘（唯一真相）
      │  每天 02:00，服务器上的程序去比对并拉取
      ▼
 服务器 43.98.163.46  /mnt/newdisk/wps-mirror
      │  Syncthing 实时分发
      ▼
 管理层各自电脑上的文件夹（只读副本）
```

**方向是单向的**：WPS → 服务器 → 管理层。
反过来不成立——谁在服务器上或自己电脑上改了文件，都不会传回 WPS，而且会在下次同步时被覆盖掉。

## 二、三个角色，各管一段

| 角色 | 是谁 | 负责什么 | 什么情况找他 |
|---|---|---|---|
| **内容负责人** | MOMO（蒋辰汐） | WPS 上的文件内容；这套同步用的是他的账号授权 | 文件内容不对、少了某份文件、需要调整同步哪些库 |
| **服务器运维** | 公司运维 | 服务器、磁盘、Syncthing 服务、程序运行 | 文件夹长时间不更新、同步报错、磁盘满、要加/减接收人 |
| **使用方** | 管理层 | 只读消费 | —— |

## 三、授权凭证（这条已经不用人操心了）

同步用的是 **MOMO（蒋辰汐）本人账号**的授权，不是任何应用身份，也不挂在技术实现方名下。
已在服务器上核实：`user me` 返回 `蒋辰汐`。

### 会不会过期？——只要天天在跑，就不会

凭证（refresh_token）**是滚动续期的**：每刷新一次，有效期重新计算 365 天。
同步每天跑，每天至少刷新一次，所以到期日每天都在往后推。

2026-09-21 实测验证过：

```
刷新前  到期 2027-09-21 12:37:26
刷新后  到期 2027-09-21 13:04:43      顺延量 = 两次刷新的间隔
```

所以**不需要在日历上记到期日，也不需要每年重新授权一次**。

### 真正的风险是什么

**连续很久没有成功刷新过**——比如同步停摆几个月没人发现，或账号被停用、权限被撤销。
这种情况下凭证会走向到期，而且到期后不会自动恢复。

这个风险已经做了兜底：每轮同步都会把**授权剩余天数**写进
`LAST_RUN` 和使用方文件夹里的 `_同步状态.txt`：

```
授权剩余      ：364 天（每次同步自动顺延；到期日 2027-09-21）
```

- 正常运行时这个数字会一直停在 364 天左右
- **数字开始明显往下掉，说明同步已经有一阵子没成功了** —— 这是真正该警觉的信号
- 少于 60 天会自动加上 `!! 请尽快处理`
- 授权真的失效时，会直接显示 `!! 失效 —— 需要 MOMO(蒋辰汐) 重新授权`

### 万一真需要重新授权

由 MOMO 本人执行（几分钟）：

```bash
ssh WPSIN@43.98.163.46
export WPS365_CLI=/home/WPSIN/.local/bin/wps365-cli
$WPS365_CLI auth login --device --scopes "kso.drive.readwrite kso.doclib.readwrite kso.file.search"
```

命令会给出一个网址和验证码，用 MOMO 本人的 WPS 账号登录确认即可。

> **两个坑**：
> 1. CLI 给出的链接如果是 `http://` 开头，**必须手动改成 `https://`**，
>    否则登录页会无限刷新且永远登不进去（浏览器地址栏会隐藏协议前缀，看不出区别）。
> 2. 动凭证之前先备份 `/home/WPSIN/.config/wps365-cli/` 整个目录。
>    `auth setup` 会覆盖已有凭证，填错就找不回来了。

## 四、怎么确认它还活着

### 最简单的办法：打开文件夹看一眼

文件夹根目录有个 **`_同步状态.txt`**，每天自动重写：

```
最后一次同步完成：2026-09-21 19:32:10
本次结果        ：正常
文件夹内容      ：23048 个文件 / 13G
```

**只要这个日期是昨天或今天，系统就是好的。** 超过两天没更新，找运维。

### 运维侧的查法

```bash
ssh WPSIN@43.98.163.46
cat /home/WPSIN/wps-sync/LAST_RUN          # 上次运行结果摘要
tail -50 /home/WPSIN/wps-sync/sync.log     # 详细日志
crontab -l                                  # 确认定时任务还在
```

## 五、故障对照表

| 现象 | 多半是什么 | 怎么办 |
|---|---|---|
| `_同步状态.txt` 几天没更新 | cron 没跑，或程序卡住 | 运维：`crontab -l` 确认任务在；`ps -ef \| grep wps_mirror` 看有没有卡住的进程 |
| 日志里大量 `403` / `userNotLogin` | 授权失效 | 如果已过 2027-09-21，按第三节重新授权；否则找 MOMO 确认账号状态 |
| 日志出现 `[熔断] 本轮将删除 N/M 个文件` | **保护机制生效了，没有删东西** | 别急着放行。先查清云端是不是真删了那么多，多半是扫描出了问题。详见第六节 |
| 日志出现 `[跳过] 上一轮同步仍在运行` | 正常现象 | 不用管。上一轮没跑完，本轮自动让路 |
| 磁盘告警 | 镜像约 13G，会随 WPS 内容增长 | 运维扩容或清理。当前 `/mnt/newdisk` 余量 700G+ |
| 管理层说文件夹里少东西 | 先确认 WPS 上有没有 | WPS 上没有 = 正常（源头就没有）；WPS 上有 = 找运维查日志 |

## 六、关于「熔断」——请务必读这一节

程序有一道保护：**单轮要删除的文件超过总量 10%（且超过 50 个）时，中止清理，一个文件都不删。**

这道保护是有来历的：2026-09-21 调试时用 `--drives` 只扫了一个库，
程序把其余 23,047 个文件当成「云端已删除」，把 13G 镜像清空了。
当时还没有这道保护。

**所以如果你看到熔断日志，正确反应是去查为什么扫描少了，而不是加参数放行。**

放行参数是 `--allow-mass-delete`，只有在**确认 WPS 上真的删了这么多文件**时才用。

同理，任何时候用 `--drives` 限定范围跑，程序都会自动跳过清理——局部扫描没有资格判断全局删除。

## 七、还需要运维做的一件事

**给 Syncthing 的这个 folder 打开 File Versioning（简单版本控制，保留 5 个版本）。**

理由就是第六节那件事：这是单向同步，服务器上的删除会**原样传播**到所有管理层的电脑。
源头一旦误删，没有版本库就找不回来。开了版本控制，误删的文件会进 `.stversions`，还能捞。

> 程序已经在 `.stignore` 里排除了 `.stversions` 和 `*.part`，不会和版本库打架。

## 八、要改同步范围怎么办

目前同步 WPS 上的**全部 11 个库、全部文件类型**（含图片、扫描件）。

如果将来要缩小范围（比如不要图片），改 `/home/WPSIN/wps-sync/run_sync.sh` 里那行命令的参数：

| 想要的效果 | 加什么参数 |
|---|---|
| 只要文档和表格，跳过图片 | `--only-docs` |
| 只同步指定的几个库 | `--drives "合约管理,实收数据"` |
| 先看看规模再决定 | `--dry-run`（只统计不下载） |

**改完范围后第一次跑，一定会触发熔断**（因为大量文件"消失"了）。
这是预期行为——确认新范围正确后，用 `--allow-mass-delete` 跑一次让它对齐，之后恢复正常。

## 九、这套东西的边界

- **不写回 WPS**：程序只读，不会修改、删除云端任何文件。
- **不做 OCR**：扫描件 PDF 同步过来是原样的图片型 PDF，没有文字层。要提取内容由使用方自己的工具处理。
- **有延迟**：WPS 上改了，最长要等到第二天凌晨 2 点之后才会出现在文件夹里。这一点业务方已确认接受。
- **数据敏感**：内容含保单号、客户姓名、身份证号、银行账号。
  服务器目录权限为 770（WPSIN 写、admin 读、其他人无权限），
  Syncthing 的接收人名单由运维控制，与 WPS 本身的权限体系相互独立——**加人时要单独确认是否该看**。
