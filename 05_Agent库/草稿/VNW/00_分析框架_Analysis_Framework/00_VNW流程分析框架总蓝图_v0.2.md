## 0. 三层结构必须分开

| 结构 | 核心问题 | VNW 里对应什么 |
|---|---|---|
| **分析框架** | 该问什么、如何证明 | 认知层（域结构/流程全景图）+ 命题体系 + 分析模型库 |
| **数据流水线** | 信息如何进入并成为证据 | Postgres权威源 → `sync_data_foundation.py` → T1-T30 → `l3_model_builder.py` → model_snapshots |
| **Agent运行系统** | 谁在何时执行什么动作 | `l3_analysis_runner.py`（真实LLM）+ `agent.py` CLI（人工触发）+ 30分钟只读扫描 |

三者关系：数据流水线提供可用证据，分析框架约束如何使用证据（该问什么问题、命题要达到什么等级才能进报告），Agent运行系统负责按约束执行并留痕。v0.1 把这三件事写成一份"六层清单"，导致"认知层维度"和"数据ETL"混在一起讨论，"命题该怎么定级"和"谁去跑分析"也混在一起——这次拆开。

## 1. 分析框架（该问什么、如何证明）

### 1.1 认知层——流程全景图与域结构

不新造叙事，复用面板E已在用的链路：`L2能力 → L3目标 → L4交付物 → 具体能力/AI介入方式 → 价值节点`。"流程全景图"是把这条链路从"逐L3展示"升级成"跨L3/跨域可比较"的聚合视图。

**域结构（真实数据，T1.domain字段，19域/74个L3）**：

**已知数据质量问题（处理原则，不是等修好再往下走）**：3处domain冲突（L3-IBRD/URD/CFM，同一l3_code在T1里对应两个domain）保持"未定归属"显式状态，不自动二选一；至少18个L3缺失domain保持"MISSING"显式状态，不用前缀猜测。这两条处理原则本身就是认知层的一部分。

业务集群归纳（⚠️ 我从L3/交付物名称反推，需 Jasper 确认真实业务语义）：渠道与获客生态（EQ+PARTNER+KA+NG+SMPS）/理财师渠道运营（FA+PAY+BSRV+JOPD+USV）/保险产品与保司合作（INS+IBRD+CRR+SSVA）/风控合规（RCM+URD+CPM）/支撑职能（HR+TREASURY）。

### 1.2 命题体系（改造自 HKIA 的 Fact/Evidence/Claim，适配 VNW 已有的四层证据分级）

VNW 已有"数据库事实>正式复核>材料补充>工作坊共识"四层证据分级，这是**证据来源可信度**分级，不是**命题本身确定性**分级——两者要分开，VNW 目前缺后者。借鉴 HKIA 的 A/B/C 命题分级，定义 VNW 版本：

| 等级 | 定义 | 要求 |
|---|---|---|
| A | 直接由数据库权威事实证明，不需要额外推导 | 单一 `evidence_id` 可直接验证，如"L3-HRA的Gate A=BLOCKED" |
| B | 多个独立证据方向一致，支撑机制但需要排除替代解释 | 至少两个独立来源/方法互相印证 |
| C | 需要 VNW 现在没有的数据才能验证 | 明确标注缺什么数据 |

**子命题不自动继承父命题等级**——这条对 VNW 同样适用：即使某个域的某几个维度打出了具体分数，也不能因此说"这个域的AI原生度评估"整体命题已验证。

**示范：给 1.3 的根因发现套上分级**——"价值节点覆盖不足是74个L3的头号真实阻断根因"这条命题：两个独立方法互相印证（VNW README 早先的定性判断 + 这次对 `gap_reasons` 的定量聚合），方向一致，**评为 B 级**；要升到 A 级，还需要排除"是不是某几个域本来数据就少所以显得覆盖率低"这类替代解释——这条排除工作本轮还没做，先如实标 B，不虚报 A。

### 1.3 分析模型库

**诊断模型（已用真实数据跑通）**：

- 价值链分析：面板E的叙事链本身就是，直接复用；
- 根因分析（2026-08-03，74个L3全量聚合 `gap_reasons`）：原始频次最高的两条（"缺少可关联的规则记录"67个L3、"规则可定位L4=0/N"67个L3）核对后是完全相同的67个L3，且数据里明确标注"不阻断建模"，是噪音。剔除后真实阻断原因排序：

  | 排名 | 真实阻断原因 | 影响L3数 | 占比 |
  |---|---|---|---|
  | 1 | 存在熔断或无价值节点 | 44 | 59.5% |
  | 2 | 价值节点-L4映射=0 | 19 | 25.7% |
  | 3 | Gate M=BLOCKED（汇总标志） | 14 | 18.9% |
  | 3 | Gate E=BLOCKED（汇总标志） | 14 | 18.9% |
  | 5 | D1-D6完整度不足 | 10 | 13.5% |
  | 6 | 缺少可解析流程蓝图 | 4 | 5.4% |
  | 6 | 可追溯任务覆盖不足（门槛80%） | 4 | 5.4% |

  单一最大真实阻断原因占全部阻断实例的40.4%，前两名（本质是同一件事：价值节点覆盖）累计占57.8%。命题分级：**B级**（见1.2示范）。

- 帕累托分析：跟根因分析是同一份聚合数据的两种读法，不必当独立任务重做。

**AI原生度评估模型——草案（⚠️ C级命题，纯我的合成草稿，需 OB 收集真实方法论校准）**：

| 维度 | L1（纯数字化） | L2（系统辅助） | L3（Agent辅助决策） | L4（AI原生） |
|---|---|---|---|---|
| 流程设计 | 纯人工执行，系统只做记录 | 系统提供表单/审批流工具，人是决策主体 | Agent承担部分执行环节，人负责判断和例外 | Agent是流程设计的一等公民，人机协作是设计起点 |
| 决策模式 | 人凭经验决策，数据只做事后记录 | 系统提供报表/仪表盘，人看数据决策 | Agent给出预测/建议草稿，人确认或修改 | Agent自主决策常规场景，人只处理例外和仲裁 |
| 流程形态 | 流程无文档化，靠口口相传 | 流程固化成文档/流程图，变更需人工修订 | 流程有预设条件分支，能按输入类型走不同路径 | 流程能根据实时反馈动态调整路径 |
| 组织架构 | 纯部门制，跨部门靠人工协调交接 | 部门制为主，少量流程有跨部门SOP/RACI | 部分能力域打破部门边界，但组织形态仍是部门制 | 组织按能力域+Agent集群运作 |
| 分析频率 | 无定期分析，靠人工发现问题触发 | 周期性分析（月/季度报告） | 部分事件触发的分析（如VNW的30分钟只读扫描），触发范围有限 | 全面事件驱动，变化发生即触发分析 |

用这套草案量VNW自己（校验草案是否可用的测试，不是正式评分）：决策模式约在L3，分析频率L2-L3之间，组织架构L1-L2，流程设计L2-L3——VNW自己没有一维摸到L4。

**组织变革模型**：完全空白，VNW数据里没有HR/组织层面信息支撑ADKAR类模型，先记录缺口，本轮不具备条件。

### 1.4 维度目录（数据流水线能支撑什么，详见第2节；这里只列分析框架需要但流水线目前没有的）

时间序列/历史趋势（现在只有当前状态快照）、AI原生成熟度五维打分字段（T1-T30完全没有）、事件/执行日志（process mining所需，大概率拿不到，不列入本轮范围）。

| 治理维度-证据分级 | evidence_registry | 完整 |

## 3. Agent运行系统（谁在何时执行什么动作）

**架构原则**：不要因为下表有6行就默认要拆成6个独立Agent进程——VNW自己的[Agent搭建SOP_v1.2.md](../../Agent搭建SOP_v1.2.md)第四节已用真实代价验证"一个Agent+skills模块"优于拆分子Agent。值得独立成Agent的只有本质跨多个业务Agent复用的能力（如治理、背景记忆）。

**现状对照**（2026-08-03核实代码得出）：

| 环节 | VNW 真实现状 |
|---|---|
| 战略规划 | 不具备。需求定义、路线图全是 Jasper 手写。 |
| 流程建模 | 具备，但机制不是"挖掘"。`skills/l3_model_builder.py` 从已有文档结构化重建，不是从执行日志反推。 |
| 分析执行 | 具备，是真LLM调用。`skills/l3_analysis_runner.py` 的 `run()` 真的调 DeepSeek API。 |
| 数据工程 | 具备，但脚本不是Agent。`sync_data_foundation.py` 是确定性脚本，触发靠人手动跑命令。 |
| 编排调度 | 基本不具备。全流程靠人工敲CLI，唯一自动调度是每30分钟一次的只读扫描（`com.jasper.vnw-source-check.plist`），不自动应用/不自动重跑/不自动发布。 |
| 输出与治理执行 | 报告是固定模板不是Agent写的；治理是硬编码规则（Gate M/E/A判定、`MODEL_DRAFT`不得静默转正）不是独立Agent；方法论转正Agent（该填治理Agent位置）还没建成。 |

**执行层面的治理规则**（区别于1.2"命题该怎么定级"这种分析框架层面的治理）：Gate M/E/A判定、熔断标记、D1-D6来源优先级——这些管的是"能不能跑/跑出来的东西能不能发布"，不是"命题够不够格进报告"，两件事故意分开放在结构一和结构三，不混在一起。

## 4. 建设方式：垂直切片，不是按层横向推进

v0.1 的优先级是"先认知层、再数据层、再分析层、再治理层、再战略层"——横向推进，容易做出空架子。改成垂直切片：每个阶段选一个真实的域，把"认知层归属→数据流水线支撑→分析模型产出→命题分级→Agent执行"整条链走一遍，只建这个切片必需的能力。

### Phase A：HR域全链路验证（建议下一步，已有部分产出）

- 输入：HR域（L3-HRA/HRM/SPE）已有的T1-T30数据+model_snapshots；
- 产出：这三个L3的完整命题链——Fact（Gate状态）→ Evidence（`gap_reasons`）→ Claim（根因判断，带A/B/C分级）；
- 验收：任意一条结论都能回答"来自哪里、用什么口径、支持哪个命题、谁签核、什么会推翻"（借用 HKIA Phase A 的验收标准，这条本身是通用方法论，不是HKIA专属）。

### Phase B：推广到全域

- 把 Phase A 验证过的命题链方法推广到全部74个L3（1.3 的根因分析其实已经是这一步的初版，只是还没有正式套上命题分级结构）；
- 处理 domain 冲突/缺失的18+3个L3。

### Phase C：接入战略层

- 等 Jasper 给出北极星指标/AI原生成熟度目标方向，把 1.3 的AI原生度评估草案跟真实目标挂钩。

### Phase D：AI原生度评估口径校准

- 依赖 OB 收集的真实行业成熟度方法论，把 1.3 的C级草案升级。

## 5. VNW 自己的"危险错觉"清单

（借鉴 HKIA `01_现状与目标缺口矩阵` 第4节的自省方式，包含这次会话里我自己犯过的错误）

| 错觉 | 实际问题 |
|---|---|
| 有74个L3快照就等于流程知识完整 | 大多数L3还是 `WAITING_INPUT`/`LIMITED_MODEL`，真正 `FULL_MODEL` 的只有个位数几个 |
| 把老板框架的六层套下来，内容填满了就是框架搭好了 | v0.1 就是这个错误——六层是从聊天中借来的通用模板，不是为VNW的问题形状（单一权威源，不是多源情报）量身定做的 |
| 数据是真的，结论就自动是A级 | 1.3 的根因发现虽然用了真实数据，但只是B级（两个独立方法互相印证），没有排除替代解释前不能标A |
| 写了草案就等于有了标准 | 1.3 的AI原生度评分口径是我自己写的，没有经过任何行业方法论校准，如果被直接拿去给某个L3打分，就是把草案当标准用 |
| 分析产出好看，说明VNW已经很成熟 | 这次会话早前我在数据/框架都没立住时先做了前端展示页，就是这个错觉的真实案例；域视图、根因分析这些做出来后容易让人觉得"已经很懂自己的流程了"，但很多L3的诊断本身覆盖率不足 |
