# VNW统一分析Spec v1.0

> 来源：参考`香港长期保险统一分析Spec体系_内部培训`(港险市场分析方法论，非照抄)+
> `generic_analysis_framework.md`(通用维度治理思路)，改造为VNW自己的分析纪律。
> 原方法论回答"某渠道市场份额是否增强"，VNW版回答**"这个L4该不该投AI、投哪种形态、
> 为什么"**——决策问题不同，但"同一堆数据为什么能吵出三种结论"这个病根是一样的，
> 治理方式可以直接搬。
>
> 首个验收案例：L3-COM。跑通后套用到其余67个L3，不再逐个重新设计方法论。

---

## 一、决策问题（每份L3报告要回答的唯一问题）

> **这个L3下的每个L4，该不该投入AI、投入Auto/Aug/Hybrid哪种形态、投入之后人力现状
> 怎么调整——结论必须能复述用的是哪份数据基线、哪条证据链、到第几级证据强度。**

不回答"这个L3整体值不值得做"（粒度太粗，会掩盖L4间的巨大差异），也不回答"技术上
能不能实现"（这只是根因阶梯的第一层，不是终点）。

---

## 二、分析基线（对应原方法论的"横向合同"）

任何一份L3报告发布前，必须能一次性说清以下字段，缺一项就不能进入结论：

| 字段 | 含义 | VNW取值来源 |
|---|---|---|
| 数据快照 | 本次结论基于哪个DB快照 | `snapshot_hash` |
| 分析输入哈希 | 判定分析是否已过期的依据 | `analysis_input_hash` / `analysis_run_input_hash` |
| 生成时间 | 报告生成的时间戳 | `generated_at` |
| 岗位归属基线版本 | 岗位族数据来自哪一版文档 | `2026-07-20_68L3岗位族归属设计_v6.1` |
| 人力现状基线版本 | 在岗人数数据来自哪一版文档 | `2026-07-28_人员归属方案_v5.3` |
| 业务数据基线 | 业务表匹配基于哪次核实 | `2026-08-04 122张表完整目录核实` |
| KPI基线 | KPI关联基于哪份定义 | `dim_kpi` + `bridge_kpi_l3` |

**基线过期规则**：`analysis_input_hash`与当前快照不一致时，报告状态强制降级为
`INPUT_CHANGED`，旧结论只能作为历史参考，不能当作当前结论引用——这条规则已经在
`production_status`里实现，本Spec只是把它纳入报告契约，不是新发明。

## 三、受控维度体系（对应原方法论的L2业务维度）

每个维度只归一个主责数据源，禁止同一维度在多个面板重复定义出不同口径。

| 维度 | 主责数据源 | 已实现位置 |
|---|---|---|
| L2业务能力 | `bridge_l3_l2` | `model.l2_capabilities` |
| 价值流/客户旅程位置 | `bridge_l3_vs_stage` + `dim_vs` | `model.value_stream_mappings` |
| 岗位归属 | `68L3岗位族归属设计_v6.1` | `l4.position_family` |
| KPI关联 | `dim_kpi`（定义）+ `bridge_kpi_l3`（Mark战略权重草稿） | `model.kpi_mappings` |
| 业务数据证据 | `public`/`comm_sandbox`/`fin_sandbox`122张表 | `l4.business_evidence`（四维：产出/规则/流程状态/追溯） |
| 人力现状 | `2026-07-28_人员归属方案_v5.3` | 岗位族层面聚合人数（不精确到个人） |

## 四、双轴声明规则（对应原方法论的"多口径并列"，直接来自我们自己的真实教训）

VNW判断一个L4能不能AI化，天然存在**两套不可合并的口径**：

- **D1-D6/Tier轴**：技术上能不能自动化（输入结构化/规则清晰/输出可验证/接口可达/
  失败可降级/合规约束），来自`dim_process`
- **候选Agent封装轴**：这个动作是否已经参数化到可以直接封装成Skill（A-高封装 /
  B-中封装 / C-低封装 / F-不建议），来自`L4流程_Skill封装可行性评估`

**真实案例**：银行账户管理Agent在候选Agent口径下是100% A档（高封装），但在
D1-D6/Tier口径下70%是Hybrid（需人工判断）——两套体系回答的问题不同（"能不能包装
成一个可执行的动作"vs"要不要人工审核这个判断"），**禁止合并成一个综合自动化分数**。

**规则**：
1. 报告必须把两轴并列展示，不生成加权综合分
2. 当两轴结论方向相反（如Tier=Hybrid/Human但候选Agent=A/B高封装），必须显式标注
   `axis_conflict`，作为需要业务方澄清的信号，而不是自动选一个"更准"的口径

## 五、证据分级 A/B/C（复用已有的EvidenceClass/EvidenceStatus，不新造体系）

VNW的`tools/evidence.py`里`EvidenceClass`（AUTHORITATIVE/SUPPLEMENTAL/DERIVED/
CONSENSUS）+`EvidenceStatus`（ACTIVE/MISSING/CONFLICT/STALE/UNVERIFIED）已经是
一套完整的证据来源治理，本Spec只是把它翻译成人可读的A/B/C语言，不重新定义：

| 等级 | 条件 | 例子 |
|---|---|---|
| **A级** | `AUTHORITATIVE` + `ACTIVE` | DB权威字段（D1-D6、dim_vn判断、蓝图步骤） |
| **B级** | `SUPPLEMENTAL` + `ACTIVE` | 已核实的补充材料（68L3岗位族文档、业务数据仓库匹配、Skill封装评估VERIFIED） |
| **C级** | `CONSENSUS` 或 `UNVERIFIED` | 业务方口头确认待书面佐证（Skill封装PROVISIONAL）、KPI战略权重草稿（`weight_confirmed=pending`） |
| **缺口** | `MISSING` / `CONFLICT` / `STALE` | 不作为证据引用，直接在报告里写"待补" |

报告中每条结论性表述后标注等级，C级结论必须同时写出"待谁确认、确认后升级到什么
状态"，不能用C级证据支撑最终定档结论。

## 六、根因阶梯（对应原方法论的四层根因树，纯程序计算，不新增LLM生成环节）

每个L4的"该不该投AI"判断拆成四层，层层继承，越往下越需要更强证据：

```
① 事实层（A级，D1-D6数据）
   → ② 机制层（A/B级，候选Agent封装档位+推荐路径）
      → ③ 结构层（B级，业务数据四维证据：产出/规则/流程状态/追溯 + 岗位归属）
         → ④ 策略层（C级草稿，KPI关联 + 价值流位置 + 优先级）
```

- **①事实层**：D1-D6是否完整、当前Tier是什么——回答"技术上能不能"
- **②机制层**：候选Agent档位、封装判断依据、推荐设计路径——回答"逻辑显式化到什么程度"
- **③结构层**：业务数据证据类型（有规则证据=逻辑已参数化，有流程状态证据=能看到人工关卡在哪）+ 当前负责岗位——回答"现实里数据和人力基础打得牢不牢"
- **④策略层**：KPI关联（含权重是否confirmed）+ 价值流位置（是否在断点旅程上）——回答"值不值得优先投入"，这一层C级证据居多，是需要业务方确认的部分

四层任何一层缺失，报告必须显式写"待补"，不能跳级下结论（这正是原方法论"根因分析
不能一步跳到客户偏好"的VNW版本）。

## 七、面板/页面合同（对应原方法论的Figure×Insight）

现有Panel A-F已经有`PanelMeta`（SSOT+分析逻辑）的雏形，本Spec在此基础上补两层：

1. **逐面板Insight**：每个面板结尾补一句"本面板给出的判断"（不是重复面板内容，是
   提炼），Gate面板→"当前处于哪个准入状态、卡在哪条规则"；Panel E交付物地图→"哪些
   L4已具备强证据、哪些还是数据空白"
2. **跨面板综合判断**：报告末尾新增"综合判断"区块，把根因阶梯四层拼成一段可复述的
   结论，附状态标记（见第九节）

## 八、反模式清单（直接对照原方法论第8页，翻译成VNW版）

| 反模式 | VNW版本 |
|---|---|
| 只给比例，没有分母 | 只说"80%可自动化"，不说是18个L4里的几个、按什么口径算的 |
| 边际无Baseline | 说"较上次分析有提升"，不说上次分析的`analysis_input_hash`是什么 |
| 图后无Insight | 面板贴数据表，不给"这说明了什么" |
| 结论越级 | 把候选Agent"A档"直接翻译成"应该自动化"，跳过了Tier轴和业务方确认 |
| **VNW特有：两轴合并** | 把D1-D6 Tier和候选Agent档位加权成一个分数（第四节明令禁止） |

## 九、结论状态机与团队角色（对应原方法论"四角色协作"）

| 角色 | 对应PDF角色 | 职责 |
|---|---|---|
| VNW Agent（自动生成） | 数据守门人 | 产出事实层+根因阶梯草稿，标注证据等级，不代替业务判断 |
| Jasper / L3业务负责人 | 分析负责人 | 对综合判断做最终定档，把status从DRAFT改为CONFIRMED |
| 相关业务方 | 业务挑战者 | 对C级结论、axis_conflict提出替代解释或补充证据 |
| 决策确认记录 | 编辑/发布记录 | `07_接入记忆_Integrate_Memory/analysis_confirmations/L3-XXX.json`，落盘存证 |

**状态机**：
```
DRAFT（VNW自动生成，仅供参考）
  → 业务方复核C级结论、澄清axis_conflict
    → CONFIRMED（Jasper/业务负责人签字，写入analysis_confirmations/L3-XXX.json）
```

**明确规则：DRAFT状态的综合判断不能当作最终结论对外呈现或用于投入决策**，前端和
导出的报告都必须显著标注当前状态。

## 十一、与`generic_analysis_framework.md`的取舍

那份文档更像知识库目录模板，价值在"受控维度要有主责归属"和"先建骨架再填内容"两条
原则——已经吸收进第三节和本文档结构本身。它的行业分析模型库（PEST/SWOT/波特五力等）
不适用于VNW（VNW分析的是内部L3流程能不能AI化，不是外部市场竞争），不采用。
