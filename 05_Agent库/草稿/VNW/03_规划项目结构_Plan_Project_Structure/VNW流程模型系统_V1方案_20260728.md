# VNW 流程模型系统 V1 方案

> 版本：v0.1（设计稿）  
> 日期：2026-07-28  
> 状态：开发基线已确认，未进入开发  
> 目标：基于公司 PostgreSQL 权威数据库与 OB 知识库，自动识别可建模 L3、生成可追溯的 L3 流程模型，并把不满足条件的内容转成待补清单。  
> 约束：V1 只读数据库和知识库，不反向覆盖源头；所有事实、材料补充、系统推导、工作坊共识必须分层展示和独立留痕。

---

## 1. 方案结论

V1 不应继续为每个 L3 手工复制 HTML，而应把已验证的 IRI、IBRD 两个 Demo 抽象为一套“流程模型生成系统”：

```text
PostgreSQL 权威事实 + OB/文件材料补充
                ↓
          证据归一与溯源
                ↓
          L3 条件核验引擎
          ↙              ↘
   可生成流程模型       生成待补清单
          ↓                  ↓
  负责人工作坊评审  ←—— 补建后重新核验
          ↓
      形成 AIT 候选
```

系统的核心产出不是“漂亮页面”，而是四类可核验结果：

1. 哪些 L3 可以生成基础流程模型；
2. 哪些 L3 可以进入 AI 任务评估；
3. 哪些 L3 已达到 AIT 移交条件；
4. 哪些 L3 缺什么、依据是什么、由谁补、补到什么程度才算完成。

1. L3 模型机会台；

- 不承诺实时同步，V1 采用显式重建。

## 4. 证据治理：禁止编造的系统机制

### 4.1 四级内容类型

所有字段、判断、卡片和结论必须携带 `evidence_class`。

| 类型 | 编码 | 含义 | 可否直接作为公司事实 |
|---|---|---|---|
| 权威事实 | `AUTHORITATIVE` | PostgreSQL 权威库直接查询 | 可以 |
| 材料补充 | `SUPPLEMENTAL` | DB 缺失时，由 OB/蓝图/01-05 文件补充 | 需显示来源与置信度 |
| 系统推导 | `DERIVED` | 按公开规则从事实或材料机械计算 | 需显示公式和输入 |
| 工作坊共识 | `CONSENSUS` | 负责人拖动、调整、确认形成 | 不能冒充数据库事实 |

缺失内容使用：

- `MISSING`：确实没有；
- `CONFLICT`：不同来源冲突；
- `STALE`：来源版本失效或被删除；V1 只进入审计记录，不进入业务模型；
- `UNVERIFIED`：有材料但尚未获得业务确认；V1 只进入待补清单，不进入补充层展示。

### 4.2 每条内容的证据包

建议 V1 内部统一使用以下结构：

```json
{
  "field_name": "l4_deliverable",
  "value": "《整合就绪确认书》",
  "evidence_class": "AUTHORITATIVE",
  "source_system": "PostgreSQL",
  "source_object": "process_analytics.dim_process",
  "source_key": "L4-IRI-05",
  "source_field": "l4_deliverable",
  "source_version": 1,
  "observed_at": "2026-07-28T00:00:00Z",
  "confidence": "HIGH",
  "transform_rule": null,
  "conflict_status": "NONE"
}
```

知识库补充还必须记录：

- `note_path`；
- `heading` 或 `chunk_id`；
- `note_as_of`；
- `note_status`；
- 检索方式；
- 是否存在“源文件删除/待复核”等警告。

系统推导还必须记录：

- 规则 ID；
- 规则版本；
- 输入证据 ID；
- 计算过程；
- 无法推导时的失败原因。

### 4.3 冲突处理

固定优先级：

```text
PostgreSQL 权威字段
  > PostgreSQL 其他辅助表
  > 已确认蓝图/正式SOP
  > OB知识原子
  > 其他01-05过程材料
  > 系统推导
  > 工作坊共识
```

处理规则：

1. 低优先级来源不得覆盖高优先级来源；
2. 冲突必须保留双方值，不得静默调和；
3. 页面默认展示权威值，同时显示冲突警告；
4. 没有权威值时，只有状态为生效、非待复核且来源可追溯的材料才可作为“材料补充”展示；
5. 工作坊意见单独保存，永不直接覆盖事实层。

## 5. L3 状态与条件核验

### 5.1 不使用单一完成率

每个 L3 分三道门：

#### Gate M：可生成基础模型

最低条件：

- L3 编码和名称存在；
- 至少 1 个 L4；
- 每个 L4 有名称；
- 有蓝图索引或可明确声明“无蓝图”；
- 能识别至少一种流程顺序来源。

如果只有 L4 清单、没有蓝图正文，只能生成“L4结构视图”，不能生成权威箭头、决策点和回退路径。

#### Gate E：可开展 AI 评估

最低条件：

- Gate M 通过；
- L4 有交付物；
- L4 有真实 Tier 或明确标记未评估；
- 至少能识别任务、人工控制点、规则空白中的一类；
- 能区分数据库事实与补充材料。

缺少 per-L4 业务价值时：

- 不生成差异化机会坐标；
- 可展示同一 L3 价值口径；
- 或把全部 L4 放入“待负责人归类”。

#### Gate A：可移交 AIT

最低条件：

- Gate E 通过；
- 输入数据来源明确；
- 关键规则明确；
- 输出质量门明确；
- 异常与 fallback 明确；
- 合规/授权责任明确；
- 负责人完成共识确认；
- 不存在阻断级冲突。

现有 D1-D6 只有 35/366 个 L4 完整，因此 V1 不能把大多数 L4 自动判为 AIT Ready。

### 5.2 L3 状态枚举

| 状态 | 含义 |
|---|---|
| `SOURCE_MISSING` | 缺少基础来源 |
| `MODEL_PARTIAL` | 只能生成局部模型 |
| `MODEL_READY` | 可生成基础模型 |
| `EVALUATION_PARTIAL` | 可局部评估，仍有关键缺口 |
| `EVALUATION_READY` | 可进入负责人工作坊 |
| `AIT_BLOCKED` | 有明确阻断项 |
| `AIT_CANDIDATE` | 已满足移交候选条件 |
| `AIT_ACCEPTED` | AIT 已承接 |

状态必须由逐条 Gate 结果组成，不允许仅由一个人工文本字段决定。

## 7. V1 数据产品

以下是“拟新增”的系统派生数据，不代表当前已经存在。

### 7.1 `l3_model_registry.json`

每个 L3 一行：

- L3 基础信息；
- Gate M/E/A 状态；
- 蓝图覆盖状态；
- L4 数量；
- 价值节点数量；
- 证据完整性；
- 冲突数量；
- 待补项数量；
- 模型快照版本和哈希。

### 7.2 `l3_model/{l3_code}.json`

包括：

- L2 能力域；
- L3 目标、触发、退出；
- 流程步骤与连接；
- L4 交付物；
- L4 具体能力；
- 价值节点；
- AI Tier；
- 人工控制点；
- 任务卡片；
- 机会矩阵初始状态；
- 每个字段的证据引用。

### 7.3 `l3_remediation.json`

待补任务：

- `remediation_id`；
- `l3_code`；
- 缺口类型；
- 缺失字段或冲突对象；
- 影响的 Gate；
- 当前证据；
- 建议补建内容；
- 完成标准；
- 建议责任角色；
- 优先级；
- 状态；
- 验证方法。

V1 中“建议责任角色”只能来自已有权威岗位映射；当前 366 个 L4 只有 1 个填写主责岗位，不能自动编造负责人。无数据时显示“待负责人指定”。

### 7.4 浏览器本地工作坊会话

V1 采用浏览器本地保存，不写回事实层。内部对象包含：

- 会话 ID；
- L3；
- 参与人；
- 任务卡调整；
- 象限归类；
- 调整理由；
- 共识/争议状态；
- 时间戳；
- 基于哪个模型快照；
- 是否已确认。

## 8. 前端信息架构

### 8.1 一级入口：L3 模型机会台

筛选：

- 可建模；
- 可评估；
- AIT 候选；
- 待补建；
- 存在冲突；
- 无蓝图；
- 按域、L2、负责人、价值节点筛选。

每张 L3 卡片只展示：

- L3 名称；
- 当前三道 Gate；
- L4/价值节点数量；
- 关键缺口；
- 数据更新时间；
- “打开模型”或“查看待补项”。

### 8.2 L3 模型页

统一采用已验证结构：

1. 流程蓝图；
2. 交付物与具体能力地图；
3. AI 任务工作坊；
4. 人工控制点；
5. AI 机会四象限；
6. 负责人决策；
7. 证据与来源抽屉。

显示规则：

- 有权威流程结构：正常绘制箭头和判断点；
- 只有蓝图索引、没有正文解析：显示 L4 结构，不伪造顺序；
- 无 per-L4 价值：不生成差异化坐标；
- 工作坊拖动：橙色“共识假设”；
- 数据库事实：蓝色“权威数据”；
- OB/文件材料：紫色“材料补充”；
- 系统推导：灰色“规则推导”；
- 冲突：红色“来源冲突”。

### 8.3 待补清单页

按 Gate 和缺口类型分组：

- 缺流程结构；
- 缺交付物拆分；
- 缺价值节点映射；
- 缺规则；
- 缺数据；
- 缺人工责任；
- 缺异常处理；
- 来源冲突；
- 来源失效。

每条任务必须能展开查看：

- 为什么缺；
- 来源在哪里；
- 影响哪个页面和 Gate；
- 完成后系统如何自动复核。

## 9. V1 首批判断规则

规则必须配置化、带版本号，禁止散落在前端组件。

示例：

| 规则 ID | 规则 |
|---|---|
| `M-001` | `dim_process` 存在该 L3 和至少一个 L4 |
| `M-002` | 蓝图索引存在；没有则标记模型部分就绪 |
| `M-003` | 未解析蓝图正文时，禁止生成箭头、决策和回退关系 |
| `E-001` | L4 交付物字段存在 |
| `E-002` | L4 Tier 存在，且值属于 Human/Aug/Hybrid/Auto |
| `E-003` | 缺 per-L4 价值时，禁止差异化位置 |
| `E-004` | `dim_process` 与补充材料 Tier 冲突时采用 DB，同时保留冲突 |
| `A-001` | D1-D6 全部存在，才允许进入自动 AIT 完整评估 |
| `A-002` | 熔断节点未解除时，不得判定完整 AIT Ready |
| `A-003` | 关键人工控制点缺责任人时，生成待补项 |
| `P-001` | 工作坊拖动只写共识层，不修改事实层 |
| `P-002` | OB 笔记标记待复核、源失效或非生效时，证据状态为 STALE/UNVERIFIED，且不得进入业务模型展示和推导 |

规则输出必须包含：

- pass/fail/partial；
- 证据 ID；
- 失败原因；
- 生成的 remediation ID。

- PostgreSQL adapter；
- OB adapter；
- 文件补充 adapter；
- 证据包 schema；
- 来源冲突检测；
- 快照 manifest 和 hash。

验收：

- 只读；
- 同一来源重复执行结果一致；
- 任一页面字段可追到表/字段或笔记路径；
- DB 冲突时不被低优先级来源覆盖。

### 阶段 2：L3 核验引擎与待补清单

产出：

- Gate M/E/A；
- 67 个 L3 registry；
- 待补清单；
- 数据健康报告。

验收：

- 每个 L3 状态有逐条规则依据；
- 缺触发、退出、岗位、D1-D6 等真实缺口被正确暴露；
- 无法判断时返回 UNKNOWN/MISSING，而不是补值。

### 阶段 3：动态模型生成器

产出：

- IRI 动态模型；
- IBRD 动态模型；
- 通用 L3 模型 JSON；
- 统一 React 页面。

验收：

- 动态页面与当前两个手工 Demo 的已确认逻辑一致；
- IRI 不产生虚假 per-L4 价值坐标；
- IBRD 未分类项保持待归类；
- 断开 OB 后仍可用 DB 生成基础模型，并显示补充材料不可用。

### 阶段 4：工作坊与导出

产出：

- 任务卡拖动；
- 四象限行拖动；
- 共识/争议；
- 调整理由；
- 浏览器本地会话保存；
- AIT 候选包预览。

验收：

- 共识层与事实层物理分离；
- 刷新前有明确提示；
- 导出包带模型快照 hash；
- 不发生数据库或知识库写入。

### 阶段 5：真实数据验证与试运行

验证样本：

1. IRI：单核心节点、交付型；
2. IBRD：多判断、多节点、合规型；
3. `L3-IBEC · 合作伙伴接触与初步沟通`：数据不足样本。数据库有 3 个 L4 和完整交付物、蓝图索引版本为 V1.3，但没有价值节点映射，D1-D6 均未完成，OB 混合检索没有返回该 L3 的直接业务知识。用于验证系统能否诚实生成局部模型和可执行待补清单；
4. `L3-EO · 理财师权益分级与绩效监控`：D1-D6 完整样本。数据库中 9/9 个 L4 均具备完整 D1-D6，有 1 个价值节点映射，且蓝图索引存在。OB 中存在 `EA流程架构项目/主链L4流程.md`，状态为生效、权威层为 `02_定稿`、置信度 HIGH，可作为合格补充材料，用于验证完整评估与 AIT Gate。

验收遵循 Agent SOP v1.2：

- 确定性检查优先；
- 独立数据源交叉核验；
- 异常特征清单；
- 真实脏数据验证；
- 生成者与验证者分离。

## 11. 测试矩阵

### 11.1 确定性测试

- schema 校验；
- 行数和唯一键；
- FK/桥接孤儿；
- 枚举合法性；
- 每个显示字段都有 evidence ID；
- DERIVED 必须有 transform rule；
- CONSENSUS 不得出现在 AUTHORITATIVE 输出；
- 缺值不得被空模板替代；
- 快照幂等；
- 同一 L3 重跑 hash 一致。

### 11.2 异常特征

首批加入：

- 没有 per-L4 数据却出现不同坐标；
- 蓝图正文未解析却出现决策箭头；
- OB 待复核笔记被当作权威事实；
- 数据库与文件冲突但页面无警告；
- Auto 被解释为岗位完全替代；
- 熔断未解除却显示 AIT Ready；
- D1-D6 缺失却给出总分；
- 工作坊调整被写成数据库结论；
- 价值节点与 L4 无映射却声称一一对应；
- 重复组合交付物被自动拆分后未标“待确认”。

### 11.3 人工业务验收

负责人只需要确认：

- 流程是否反映实际执行；
- 交付物是否正确；
- 人工控制点是否正确；
- 待补清单是否可执行；
- 工作坊共识是否可以作为 AIT 下一阶段输入。

业务负责人不负责验证数据库技术实现；技术校验由自动测试承担。

## 12. V1 成功标准

V1 完成时必须达到：

1. 67 个 L3 都有明确状态，不要求都可建模；
2. 每个不可建模 L3 都有真实待补原因；
3. IRI、IBRD 从同一生成器生成，不再依赖独立手工 HTML；
4. 任意结论最多两步可打开来源；
5. 权威事实、材料补充、系统推导、工作坊共识不会混淆；
6. 不存在已知的虚假差异化坐标、虚假负责人、虚假流程关系；
7. 全流程只读；
8. 连续两次构建结果幂等；
9. 真实数据测试通过；
10. Jasper 完成 V1 业务验收后，才讨论反向同步和正式部署。

### 13.3 本地保存边界

浏览器本地保存仅用于：

- 任务卡移动；
- 四象限归类；
- 共识/争议状态；
- 调整理由；
- 当前选中的受众视图；
- 工作坊会话草稿。

必须同时保存：

- 所属 L3；
- 所依据的模型快照 hash；
- 保存时间；
- 内容类型固定为 `CONSENSUS`；
- “仅本机草稿、未写入权威源”的提示。

数据库、OB、蓝图或系统模型快照更新后，如果 hash 不一致，旧工作坊草稿必须标记“基于旧版本”，不能自动合并到新模型。
