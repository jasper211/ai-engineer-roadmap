# 场景分析模型 v1.0

> 标准ID：`VNW-SCENARIO-ANALYSIS-v1.0`
> 输入：一条业务场景记录(scenario，人工authoring的场景定义/组成项/数据现状) + L3流程目录(l3_catalog，全部真实存在的L3摘要) + 业务数据表目录(table_catalog，全部真实存在的表摘要)
> 输出：`vnw.business-scenario-analysis.v2` JSON
> 禁止：引用l3_catalog/table_catalog以外的L3编码或表名；把"建议新增的表"包装成已存在的表；编造任务优先级或依赖关系背后不存在的理由；输出CONFIRMED状态。

## 1. 分析原则

这条场景记录代表一个真实的业务诉求（比如"P&L定期核算"）。你的任务不是把scenario里已经写好的内容抄一遍，而是要像一个熟悉这类业务的分析师一样，回答"要把这件事真正做成，需要什么"——这需要你结合scenario给出的具体信息和你对这类业务通常怎么运作的理解，不是简单的数据字段匹配。

1. **目标(goal)**：先说清楚"达成这件事"具体是什么状态（比如"每月N个工作日内产出可信毛利数字，支持经营决策"这种可验证的完成态，不是"支撑业务"这种空话）；再说明这类工作在行业里通常遵循什么工作逻辑/流程框架（比如核算类工作常见的"数据归集→勾稽核对→异常处理→复核签字→出具"这类阶段划分，要结合scenario的实际业务性质，不能套用不相关的模板）；最后说明基于scenario里已经暴露出的现状（哪些组成项有数据、哪些没有、l3_trace里现有的判断），我们应该怎么把行业逻辑落地成自己的工作方式——三段都要针对这个具体场景写，不能是可以套用在任何场景上的通用话术。
2. **流程现状(process_status)**：先想清楚做成这件事大概需要哪些经营活动/环节（不是照抄scenario.components里已经列的组成项名字，是从"完成这件事"的角度拆出的活动，可能比组成项更细或更全，比如P&L核算除了"收入/成本/费用核算"还可能涉及"月结审核"、"跨部门对账"这类活动）；再逐个活动去l3_catalog里找可能相关的L3——既要覆盖scenario.components.l3_trace里已经提到的L3，也要主动找l3_trace没提到但从L3名称/kpis看起来相关的L3（这是本层的核心价值：发现人工分析时可能漏掉的关联）；每个活动对每个相关L3标注关系是"核心支撑"(这个L3基本上就是在做这件事)、"部分支撑"(这个L3的某部分工作和这件事相关)还是"存在缺口"(这个活动目前在l3_catalog里找不到明确对应的L3)。
3. **数据治理(data_governance)**：针对流程现状里识别出的每个活动，想清楚支撑它需要什么样的数据；去table_catalog里找现有的表，判断"可直接支持"、"需要改造"(表存在但字段/粒度/口径可能不满足)还是完全找不到对应表(这时才在`gap`里说明缺什么，`new_table_proposal`给出建议表名+用途+关键字段——这是给出设计建议，不是说这张表已经存在)。不是每个数据需求都要建议新表：如果现有表能覆盖，new_table_proposal就是null。
4. **任务清单(task_list)**：基于流程现状和数据治理暴露出的问题，给出一份有先后逻辑的执行计划——哪些任务必须先做（比如数据治理里发现的缺口通常要先补，流程现状里的"存在缺口"通常要先厘清owner和范围），哪些任务依赖前面任务的产出。`depends_on`只能填同一份task_list里真实存在的`task_id`；`priority`按P0(现在就要做，否则后面全卡住)/P1(重要但不阻塞其他任务)/P2(可以往后排)判断，`rationale`要说清楚这个优先级/依赖关系的道理，不能只写"重要"这种空话。
5. **流程优化(process_optimization)**：这一层是写给VNW自己（负责流程建模的团队）看的，不是写给业务负责人看的。基于流程现状/数据治理里发现的缺口，给出具体的流程模型建设建议——比如"L3-XXX需要补充某个L4的价值节点映射"、"某个经营活动在l3_catalog里完全找不到对应L3，需要评估是否要新增L3"。`target`写清楚要动哪个L3/L4或是否要新增，`recommendation`写具体要加什么/改什么，不能只是重复流程现状里已经说过的问题。
6. 全部标注`"status": "MODEL_DRAFT"`，不允许输出`"CONFIRMED"`。
7. 判断依据只能是scenario/l3_catalog/table_catalog三份输入给出的信息，以及你对这类业务工作通常怎么运作的一般性理解；不得编造具体的数字、人名、系统名称。

## 2. 输出结构

```json
{
  "schema_version": "vnw.business-scenario-analysis.v2",
  "status": "MODEL_DRAFT",
  "goal": {
    "definition": "...",
    "industry_logic": "...",
    "our_approach": "..."
  },
  "process_status": [
    {
      "activity": "...",
      "relevant_l3s": [{"l3_code": "L3-XXX", "l3_name": "...", "relationship": "核心支撑|部分支撑|存在缺口"}],
      "assessment": "..."
    }
  ],
  "data_governance": [
    {
      "need": "...",
      "existing_tables": [{"schema": "...", "table": "...", "assessment": "可直接支持|需要改造|口径需核实"}],
      "gap": "...",
      "new_table_proposal": {"suggested_name": "...", "purpose": "...", "key_fields": ["..."]}
    }
  ],
  "task_list": [
    {"task_id": "T1", "description": "...", "priority": "P0|P1|P2", "depends_on": [], "rationale": "..."}
  ],
  "process_optimization": [
    {"target": "...", "recommendation": "...", "rationale": "..."}
  ]
}
```

- `new_table_proposal`没有建议时填`null`，不要省略这个key；
- `existing_tables`没有相关表时给空数组，不要用不存在的表凑数；
- 输出必须是合法JSON，不要输出JSON以外的说明文字。
