# VNW · 07 业务数据表分析框架（持续方法论）

> **目标：把"数据库业务数据表分析"从一次性盘点，建成可持续迭代的治理流程。** 业务本身在陆续补充新表，所以这个框架必须是"每一次新增/变更都可重复跑的工序"，而不是静态文档。基于 01-06 的盘点发现沉淀。

## 一、分析的三个输出物（每轮循环都更新）

| 输出物 | 内容 | 存到 |
|--------|------|------|
| 表清单基线 | 全表 + 三维度（角色/证据/版本） | `table_role_register.csv` |
| 血缘/分类证据 | view/FK/流水线 + 语义桥接第四类连接 | data_lineage.json 增量 |
| 待人工裁定清单 | 真断点/疑似重复/待batch的表 | `99_REVIEW_待人工确认` |

## 二、六步迭代工序（新表进来时重复）

### Step 0. 接新表（基线刷新）
- 全库扫描 → 对比上轮基线 → 识别：**新增表 / 修改变更 / 新增0行空表**。
- 判定点：新表是`事实/维度/配置/视图/日志`哪类？有无指向已有表的同名字段？

### Step 1. 归版本族（先看是不是"多版本拆分"）
> 见 04_逻辑表归一化清单。凡命名含 `_history/_history_long/_snapshot/_versions/_log/_scope`，或跨 schema 同名，先查是否属于某逻辑对象族（当前/归档/快照/副本）。
- 是 → 挂 `version_group`，标 `version_role`（current/history/snapshot/duplicate/log）。
- 否 → 进入下一步。

### Step 2. 判角色（三层框架）
> 见 06_表角色分类。回答"它在业务里是啥位子"：
- ① 交付本体 → 看 evidence_type（output/rule/workflow/audit）→ 匹配L4；
- ② 服务支撑 → 通过血缘/引用找到它支撑的交付本体（视图/维度/桥接）；
- ③ 独立/工具 → 细分原因（版本/字典/空表/系统表）。

### Step 3. 连血缘（四类证据合并）
现有三类客观边（view依赖 / FK / 流水线同批）+ **第四类业务语义连接**（bridge 的 evidence_type）：
- ①②类优先接入语义连接（不造假边）；
- 记录每张表"是否真实血缘 / 是否语义已认领 / 是否真断点"三种状态区分。

### Step 4. 标僵尸——诚实口径（关键改正）
> **把"是否挂L4"从"是否僵尸"脱钩**。一张表标僵尸需同时满足：
- 有真实数据（>0行）**且**
- 血缘查不到谁产出/谁消费（非版本/映射/字典）**且**
- 语义层也没认领（非规则/流程状态证据）
- 三个答案都"是"才算 `suspected_zombie`（纳入`99_REVIEW`待人工核实），**否则不是僵尸**：
  - 版本/快照 → 补版本指针，不标僵尸；
  - 配置/规则/维度 → 标"语义未排到"，不标僵尸；
  - 0行空表 → 标 `never_activated`。

### Step 5. 回写与留痕（双写）
- 结果写入 `table_role_register.csv` + 当日 owner_updates + 主台账（见库治理规则）；
- 新确认的 L4 关联回填 bridge 语义层，反向喂给血缘图。

## 三、持续运转机制

- **触发器**：① 新表入库 ② 每日差异体检（跑 203 差异体检脚本）③ 每批 bridge 扩展 ④ Gate Review 裁定疑似重复/真断点。
- **不倒退原则**：分析从"假定有用"出发，只有铁证才标僵尸/废弃；"未排到"与"确认无关"严格区分。
- **证据分级**：SQL/FK（客观硬证据）> 语义桥接（人工核实 has_l4）> 命名/引用推断（只作候选）；三类不得混淆强度。
