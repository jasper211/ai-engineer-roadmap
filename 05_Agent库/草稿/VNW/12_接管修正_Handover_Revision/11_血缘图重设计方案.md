# VNW · 11 数据血缘图界面重设计方案

> **Mark 诉求**：104张表（及未来持续读进被分析的表）要**清晰看到分类分层分级**；**每张表有自己的卡片**（读介）；能看**表与L3-L4、岗位的关系**；**最重要的是表与表之间的关系**。
> 设计基于真实数据结构：`data_lineage.json`（edges/nodes）+ `table_analysis.json`（layer2.related_l3_l4 / positions）+ `l3Models.ts`（岗位/gate）。

## 一、为什么要重设计（现状的根问题）
1. **104张表硬塞进一张1100×820力导向大网** → 必然绕成"毛线团"，节点重叠、连线乱穿，分层分级完全看不出。
2. **一进界面就满屏颜色+字母角标+虚线** → 生态位色/关系状态/证据角标/版本标记全压在一个点节点上，信息过载、主次不分。
3. **没有"分层叙事"** → schema、table_type、L3/L4、岗位这些本就有的层级信息没被用起来做导航，全摊成平层圆点。
4. **新表加入会加剧混乱** → 力导向图每次加节点都重排，无稳定结构。

> 结论：**问题不在"画得不够好"，而在"把104张表一次性当一张网展示"这个交互模型本身。** 必须改成**分层聚焦式**浏览。

## 二、新界面的信息架构（三层导航 + 卡片 + 关系子图）

```
┌────────────────────────────────────────────────────────────┐
│ 顶部：全局统计带（表数 / 分类数 / 已确认L4 / 真断点 / 血缘边）│
├────────────────────────────────────────────────────────────┤
│ 左栏：TREE 导航（三层钻取）         │ 中栏：分类卡片浏览       │
│  ├ Schema ─ public/comm/fin       │  ┌──────────────┐        │
│  │  └ 分类 ─ 事实/维度/配置/视图… │  │ [表卡片]      │ 卡片按 │
│  │     └ L3 代码 ─ 该L3用到哪几张  │  │ 分类|分级|角色│ 当前树 │
│  ├ 按 L3/L4 语义层                  │  │ L4关联|岗位  │ 过滤结果│
│  ├ 按 岗位                           │  │ 入度x 出度y  │ 网格排布│
│  └ 按 真断点/待人工 之类特殊视图      │  └──────────────┘        │
├────────────────────────────────────────────────────────────┤
│ 底部/侧边：关系子图面板 —— 点卡片后展开「这张表的血缘子图」      │
│ 用分层布局（非力导向乱局），只画该表1~2跳上下游                  │
└────────────────────────────────────────────────────────────┘
```

## 三、四个核心模块

### M1. 三体树导航（分类 · 分层 · 分级）
"分类分层分级"落在**三种维度视图**（可切换）：
- **视图A · 按Schema+表型分类**：public / comm_sandbox / fin_sandbox → 其下再按 table_type（事实表/维度表/配置表/视图/桥接表/汇总表…）折叠展开 → 最终到表。
- **视图B · 按L3/L4语义层**：L3（如L4-COM佣金、L4-RSJD人身险）→ L4 → 关联到哪些表。**直接回答"表和业务模型的分类分层"。**
- **视图C · 按岗位**：读 table_analysis.layer2.positions，按岗位分组看它经手的表——**直接回答"表和岗位的关系"。**
所选树节点 → 过滤中栏卡片列表 + 关系子图种子。

### M2. 表卡片（每张表一张，读介卡）
卡片字段（数据全有）：
```
┌  schema.table            [角色标识]
│  业务含义: business_label / layer1.fact_statement
│  类型: table_type | 行数: row_count | 数据健康: data_health
│  ├ L3/L4关联: layer2.related_l3_l4  (可点跳 L4 视图)
│  ├ 岗位: layer2.positions
│  ├ 血缘: 入度 x · 出度 y · 状态(zombie_flag/has_lineage)
│  └ 状态: ACTIVE/BLOCKED
└  [查看血缘子图]
```
卡片是"分类/分级"的最小单元，选中态亮起，点击进关系子图。

### M3. 关系子图（最重要的：表与表的关系）
不再全量一锅端。**以"焦点"展开子图**：
- 焦点=从卡片点击选中的表，或从树导航选中的L3。
- 画该焦点的**上游1跳 + 下游1跳**（可按需扩到2跳）。
- **布局用分层算法**（按血缘方向分上游→下游列的 DAG 布局），替代力导向；节点即小卡片，显示表名+类型色块，边上带"证据类型"标签（视图依赖/FK/流水线）。
- 边按 EDGE_TONE 原类型着色，保留方向箭头与证据原文。
- **可缩放/拖拽**：子图大时 pan/zoom，而不是硬塞。

### M4. 持续可扩展（新表自动进来）
- 新表被分析后写入 data_lineage.json + table_analysis.json → 前端**自动出现**：
  - 树导航对应分类节点自动 +1；
  - 中栏卡片自动 +1 张；
  - 关系子图自动带上新关系边。
- 因是"分层 + 过滤 + 聚焦子图"，**不是全量大网**，新表不会破坏既有结构。

## 四、交互流程
1. 默认中栏显示"全部104张"卡片网格（可按 schema/分类快速筛）。
2. 点左侧任意树节点 → 中栏只显示该类表（每张仍是一张卡）。
3. 点某张卡 → 底部/右侧关系子图以它为焦点展开，高亮它的上下游。
4. 点子图另一张表 → 焦点切过去，子图重算（或"追加展开"）。
5. 顶栏特殊视图：真断点 / 待人工核实 / 0行未启用 快速入口。

## 五、技术实现建议（渐进，不破坏现有）
1. **纯前端先行**：本轮交互全用现有两个 json（data_lineage + table_analysis）就能实现，改 `DataLineage.tsx` 重组即可，**不改任何数据加工脚本**。
2. **关系图渲染**：可选
   - 轻量：继续用 SVG + 自写分层(DAG)布局与 pan/zoom（控制依赖少，改动集中在 DataLineage.tsx）；
   - 较重：引入 `cytoscape.js`（成熟血缘/图可视化，内置分层布局+缩放，但新增依赖）。
   - 倾向先轻量自写，控制风险和依赖面。
3. **表卡片列表**：用现有数据分页/分组渲染，纯 JSX。

## 六、跟「08 设计」的关系
- 08 是在旧"一张大网"模型上做"点"的视觉优化；本方案(11)是**换交互模型**——从"平层大网"变成"分层导航+卡片+聚焦子图"。两者不冲突，11 是更彻底的重设计。
- 08 里已验证的**语义**（生态位/证据/版本/僵尸诚实分类）在本方案中沉淀为：树分类维度 + 卡片徽标 + 子图节点配色，全部保留。

## 七、待确认（方向敲定再开发）

## 十一、血缘图"视觉一坨"问题 → 已改 dagre 专业分层布局（2026-08-05）

### 问题
初次实现用的自写 `computeLayeredXY` 分层太弱，一跳/二跳/全图总览节点都散成一坨。

### 修复
- 新增依赖 `cytoscape-dagre`（基于 dagre 的成熟 DAG 分层布局）。
- 弃用自写布局，改用 dagre：
  - `rankDir: 'LR'` → 上游在左、下游在右，按血缘方向**左右分层**；
  - `rankSep`(层距)/`nodeSep`(节点距)/`spacingFactor` 拉开，一跳子图更宽松(1.6)，全图总览更紧凑(1.3)；
  - 布局结束 `layoutstop` 后自适应缩放 + `cy.center()`（焦点模式把焦点表居中）。
- 移除无用函数/变量，`tsc -b` 零错误、`vite build` 成功、dev 加载正常。

### 改动文件
- `src/components/LineageGraph.tsx`：布局从 preset/自写 → dagre LR。
- `package.json`：+`cytoscape-dagre`。

### 说明
dagre 会把有向血缘按"上游→焦点→下游"分层排开，解决粘连；支持滚轮缩放/拖拽平移/点节点切换焦点。

## 十二、血缘图注释增强 + 孤立表根因说明（2026-08-05）

### 界面增强
1. **节点中文注释**：每个节点下方两行显示【业务中文名（与业务分析对齐）+ 物理表名】，文化难辨时以中文为主。
2. **图例区**（图上方横向条，HTML 绘制）：
   - 靛蓝实线 = 视图依赖（VIEW引用表）
   - 天蓝实线 = 外键关联（FK）
   - 灰虚线 = 流水线同批（同批抽取/同步）
   - 节点色：靛蓝=明细/事实表、紫=配置/维度/规则(参考)、天蓝=视图/桥接/映射、灰=0行/未启用、红=疑似断点/僵尸；边框加粗=当前焦点表。

### 孤立表根因（数据证实：48/104 张表无任何血缘边）
按类型：配置表17、维度表10、事实表5、映射表4、历史记录3、其他2、规则表2、其余各1。
按状态：suspected_zombie 19、none 15、never_activated 14。零行15张。

四类根因：
| 类别 | 数量 | 说明 |
|---|---|---|
| 参考/源料表(配置·维表·字典·映射) | 27 | 被下游读取但无 FK/view 引用登记，血缘机制抓不到；非断点，属"源料表" |
| 归档/快照/同步日志(旁路落库) | 8 | ETL 旁路落库的审计资产，通常不被业务报表引用 |
| 未激活/空表 | 15(零行) | never_activated 新装未启用 / suspected_zombie 废弃表，天然无血缘 |
| 真·可疑断点(有数据无血缘) | 少数 | 如 fact_receivable(4.7万行)、fact_insurance_plan_lines_history(4.1万行)——疑似血缘采集不完整，真实上下游未登记，属能力缺口 |

> 结论：绝大多数"孤零零的表"是**配置/维度等参考表**或**未激活/归档表**，在业务上本就无血缘；少数大表(如应收主表)无血缘则是**血缘采集缺口**，应纳入后续补采范围，而非业务上真的与其他表无关。
