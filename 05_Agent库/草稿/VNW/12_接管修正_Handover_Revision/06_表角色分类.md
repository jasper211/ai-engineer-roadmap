# VNW · 06 表角色分类：104张业务表的三层框架

> **由 Mark 的问题导出："有些表挂L4，有些表是为挂L4的表服务的、天然和L4没关，对吗？"——回答：方向正确，但要精确化为三层角色，并以真实数据落位。全部基于只读 data_lineage.json + business_data_bridge.py，不改原文件。**

## 一、核心结论

> 104张业务表**不是一维的"是否挂L4"，而是三维角色**：
> - **① 交付本体表（41张）**：内容就是L4交付物本身的数据/规则/流程状态，直接挂L4；
> - **② 服务支撑表（30张）**：不直接挂L4，但被①经血缘引用，是整条数据链的底座（视图/维度/桥接）——**价值极高，不是僵尸**；
> - **③ 独立/工具/配置表（33张）**：既未挂L4也无血缘连接（维度字典/系统表/空表）。

## 二、① 交付本体表（41张）—— 直接挂L4

> 这些表由 business_data_bridge 人工确认到具体 L4，按证据类型分四类：

### output 产出证据（内容=交付物数据）
fact_sales_activity→L4-RSJD-01 / fact_policy→L4-COM-10 / fact_commission_rate→L4-COM-01 /
fact_receivable→L4-COM-10 / fact_receipt→L4-COM-11,16 / fact_insurance_plan_lines→L4-RSJD-04 /
agg_sales_base→L4-FBA-01|RSJD-02 / agg_source_commission_wide→L4-COM-08 /
agg_market_commission_tier_rate→L4-COM-08 / fact_target→COM-04|HRA-02|HRM-01 / …（共约26张）

### rule 规则证据（判断逻辑已参数化）
config_table_type_def→L4-COM-01 / config_table_type_product_scope→L4-COM-02 /
config_table_type_tier_pricing_rules→L4-COM-02 / dim_comm_scheme→L4-COM-01 /
config_product_commission_formula→L4-COM-01 / config_license_carrier_mapping→L4-COM-01 /
partner_tier_rules→L4-COM-12 / config_partner_routing→L4-COM-12 / …（约9张）

### workflow 流程状态证据（暴露人工关卡）
market_row_state→L4-COM-02 / market_table_header_state→L4-COM-01,18 / market_publish_event→L4-COM-03 / …

### audit 追溯证据
sync_history→L4-COM-15,16 / commission_tier_adjustment_history_long→L4-COM-05 / …

> ⚠ 注意：`dim_employee` 同时服务 6 个L4（HRA/HRM多个），`fact_target` 服务3个L4，`agg_sales_base` 跨2个L3（FBA/RSJD）——一份表支撑多L4是常态，体现"表是共享资产、L4是视角"。

## 三、② 服务支撑表（30张）—— 不挂L4，但被①引用

> 这些是交付本体的"底座"，血缘里被①引用，**天然和特定L4没直接关联，但价值极高**：
- **视图**：v_fact_sales_activity(24396行)、v_policy_current_state、v_plan_year_snapshot、v_tier_rate_readable、v_commission_tier_effective 等 → 交付本体的查询/展示层
- **维度/主数据**：dim_person(5291)、dim_customer、dim_product_id、dim_product_sku → 交付本体的参照维度
- **桥接**：bridge_person_identity(15833)、bridge_person_role、bridge_partner_ka → 交付本体的多对多关系

> 判定要点：**"不挂特定L4" ≠ "与业务无关"**。它是整条数据链的支撑，血缘/僵尸判断不能把"未挂L4"当"僵尸"。

## 四、③ 独立/工具/配置表（33张）—— 既未挂L4也无血缘连接

> 再分成明确的子类（避免统一误判）：
- **版本/快照类（真实数据，非僵尸）**：fact_commission_tier_rate_history_long(33.7万)、fact_insurance_plan_lines_history(4.1万)、sales_renewal_due_snapshot(2.9万)、fact_insurance_plan_header_history → 版本指针，本模块已单独立族
- **维度字典（全域通用）**：dim_date、dim_lookup_code、dim_role_type、dim_segmentation、dim_binder_agreement → 不专属某L4，语义层未排到
- **配置/规则**：config_product_exclusion_range、config_product_feature_type、product_risk_override、config_identity_source_map → 规则证据，但bridge未排到
- **跨schema重复/空副本**：dim_comm_scheme(public空)、config_quarter(public)、config_partner_routing(public) → 见04归一化
- **系统表**：auth_users/auth_sessions/auth_audit_log、person_match_suspect
- **0行空表**：dim_payee、dim_strategy、config_strategy_*、bridge_strategy_routing、mapping_product、map_partner_payee、config_license_cost_deduction 等

> 判定要点：**这33张要按"为什么没连上"细分，而不是一刀切标僵尸**——版本→补指针、字典→待batch、空表→记 never_activated、系统表→天然无L4。

## 五、角色 vs 证据 vs 版本 三维度合表

| 维度 | 取值 | 作用 |
|------|------|------|
| **角色** | 交付本体(41) / 服务支撑(30) / 独立工具配置(33) | 回答"这表在业务里是啥位子" |
| **证据类型** | output / rule / workflow / audit / 无 | 回答"它怎么支撑L4/AI" |
| **版本关系** | 逻辑主表 / 历史归档 / 跨schema副本 / 独立 | 回答"它是不是多版本被拆" |

## 六、落位：如何用这个框架（持续投入的入口）

- 存到 `07_治理台账` 的 `table_role_register.csv`（新表：schema、table、role、evidence_type、version_group、status、reviewed_by、review_date）；
- 新表进来时按三维度登记，**不默认标"孤立/僵尸"**，而是先归角色→判证据→看版本；
- 每次 bridge 扩展 batch，把 ③ 里的表往前移到 ①（确认L4）或 ②（通过引用找到支撑对象）。
