# Prompt Optimizer · 模板级 A/B 结论（2026-10-15）

## 结论
**不接入，不配 MCP。** 对已经工程化的规格型提示词（U020 模块1），它的两种主力模板没有带来可测的改进；分析式模板还会造成格式回退。只保留为参考：起草新的、粗糙的提示词时，可以借它的「分析式结构优化」模板出初稿，再人工收敛。

## 测了什么
- **对象**：`linshenkx/prompt-optimizer`，固定在提交 `1e1f94c`。中文模板原件放在 `upstream_templates/`。
- **方式**：没有安装应用。按应用的调用方式复现它的模板：字符串模板作为 system，原提示词作为 user；消息数组模板把原提示词以 JSON 形式注入。
- **任务**：U020 模块1，2026-09 期。输入固定为该期候选池 49 条（10/10/9/10/10，每条带原文 URL），不联网。
- **三个版本**：
  - A：现行模块1 指令。只把「检索」和「HTML」两节换成「基于候选池、输出 JSON」，其余规则原样保留。
  - B：A 经「通用优化」模板改写。
  - C：A 经「分析式结构优化」模板改写。
- **模型**：deepseek-v4-pro，temperature=0，每版跑 1 次。花费约 1.7 元（余额从 11.55 元降到 9.87 元）。

## 怎么读这个结果
- 原版已经把容易出错的点都写成了硬约束，优化模板只是换成 Role / Profile / Skills 的套路结构，加不出新信息。
- C 的回退来自模板本身：它要求输出固定的 OutputFormat 结构，把原文里机器校验依赖的格式约定冲掉了。
- B 少选 3 条、缺锚点少 2 条，这个差异在单次运行的噪声范围内，不能算改进。
- **共同问题（与优化器无关）**：三版都只选了 24–27 条。原因是候选池里很多条目自带「抓取失败 / 正文不符」的备注，模型按「不编造」规则保守弃用了。这是 9 月候选池的记录问题（`reports_complete=False`），模块1 那条线如果要复用候选池，需要单独处理。

## 局限
- 每个版本只跑 1 次、只测 1 个任务、只用 1 个模型。
- 没测「粗糙短提示词」场景，那才是这个工具宣称最擅长的。
- 测的是模板加调用方式，不是应用的界面、迭代和对比功能。
