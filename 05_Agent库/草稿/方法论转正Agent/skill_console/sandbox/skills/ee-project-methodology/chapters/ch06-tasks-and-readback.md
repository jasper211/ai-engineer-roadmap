# 第 6 章：任务拆解标准与 Readback 责任签收
（对应手册：第八节、第九节）

## Core Idea
任务按六级拆解，每项可执行任务必须写满 11 个最低字段；任务发出后要经 Readback 才算被接受——已读、收到、群里回「好的」只证明信息到达。

## Frameworks Introduced
- **六级拆解**：项目 → 工作流 → 工作包 → Action → Case → Evidence。Action 是最小可管理任务，Case 是最小真实结果单元，Evidence 是支持状态和验收的记录。
- **可执行任务的 11 个最低字段**：
  | 字段 | 要求 | 不合格表现 |
  |---|---|---|
  | ID | 全项目唯一、可追溯 | 同名事项多次出现 |
  | 动作和对象 | 明确动词、具体对象 | 推进、优化、跟进 |
  | Owner | 唯一自然人或明确最终 Owner | 部门、发言人、待定 |
  | Due | 具体日期或可检验阶段 | 尽快、后续、持续 |
  | 交付物 | 文件、数据、决策、回执或真实结果 | 完成沟通 |
  | 验收人 | 有权接收或批准的人 | 团队默认认可 |
  | 验收标准 | 字段、质量、范围和结果条件 | 看起来可用 |
  | 依赖 | 前置输入、资源、专业批准 | 未说明为什么卡住 |
  | 证据路径 | Evidence ID 和受控位置 | 只留在聊天中 |
  | 状态和 RAG | 执行状态与健康度分开 | 绿灯被写成已完成 |
  | 下一动作 | 下一步由谁在何时做什么 | 等待反馈 |
- **任务书九段主线**（用于需要恢复、跨团队或有争议的任务）：任务现状 → 事实差距 → 问题 → 根因 → 解决方案 → 交付物 → 预期结果 → 验收标准 → 时间和升级。
- **Readback 六问**：
  1. 是否接受本人的角色和任务；
  2. 第一项交付物是什么；
  3. 承诺完成日期；
  4. 实际执行自然人是谁；
  5. 依赖、资源和需要调整的事项；
  6. 不能接受时的原因、替代方案和新日期。
- **默认要求**：任务发出后一个工作日内 Readback；**沉默不视为接受**；Case Manager 记录接收日期并回写主账；Principal 对拒绝、资源缺口和跨工作流冲突作决定。

## Key Concepts
- **Action**：最小可管理任务。
- **Readback**：责任签收，确认对范围、交付、日期形成承诺。

## Mental Models
- 用「不合格表现」列反向检查任务书：出现「推进 / 跟进 / 尽快 / 待定 / 等待反馈」就不合格。
- Readback 把「通知」变成「承诺」。

## Anti-patterns
- **以「已读」代替接受**。
- **部门做 Owner**。
- **状态绿灯等于完成**。

Readback 模板（填写示意，内容为结构演示）：
| 项目 | 填写内容 |
|---|---|
| 任务 ID 和角色 | T-012，数据工作流负责人 |

| 首个交付物 | 数据字典 v0.1 |
| 承诺日期 | D 加五 |
| 实际执行人 | 具名自然人 |
| 依赖和支持 | 需要系统只读账号 |
| 调整或替代方案 | 账号 D 加二前到位则按期，否则顺延两天并写入 Decision |
| 姓名和日期 | 签名、日期 |

## Key Takeaways
1. 11 个字段缺一项，任务就不可执行。
2. 一个工作日内 Readback，沉默不算接受。
3. 有争议的任务用九段主线下达。
