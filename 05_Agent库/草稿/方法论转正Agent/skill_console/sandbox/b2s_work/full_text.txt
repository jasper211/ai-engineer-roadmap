EE项目启动与运行方法论
负责人执行手册
本手册用于帮助一个新的EE项目从目标和合作意向进入可执行状态。负责人可以直接按文中的启动顺序、角色分工、任务字段、验收方法和周度节奏组织项目，也可以据此形成项目章程、负责人任务书、执行主账和Dashboard。
核心结论  建群、开会、发任务或建立文件夹都不等于项目已经启动。项目只有在范围、共同事实、责任人、执行主账、验收证据和阶段门同时建立后，才进入受控执行。
项目开始的五项证据
一 使用范围和负责人职责
本方法适用于联合项目、产品建设、经营验证、组织改造、数据和合规建设等需要跨团队协同的工作。它不替代业务方案、法律意见、财务审批或专业技术设计。新项目应保留本文的控制结构，再根据项目风险、周期和交付对象调整工作流、字段和阶段门。
负责人必须先确认的事项
项目目标和结束决策。说明项目要验证或交付什么，以及到哪个节点决定继续、调整、扩张或停止。
范围和边界。区分当前必达、未来范围、建议方案、待核验事实和明确不做事项。
授权和资源。任命Principal、Case Manager或PM、工作流负责人、专业确认人和验收人。
第一批真实对象。至少指定一个真实客户、业务主体、产品、流程、数据集或交付Case，避免项目长期停留在框架层。
验收口径。确定交付物、证据、接受人、阶段门和未达标时的处理方式。
负责人不应替代的事项
不替业务负责人编造客户需求、经营目标、工作量或产能。
不替财务、法务、合规、牌照或数据负责人作专业结论。
不以口头认可代替Readback、签收或正式Decision。
不为赶日期跳过证据、授权、真实数据或合规阶段门。
二 六层项目控制模型
新项目按六层建立控制。每一层解决不同问题，不能用Dashboard替代主账，也不能用主账中的一行状态替代真实交付物。
三 Project层和Case层
项目应同时管理Project层和Case层。Project层建设主体、治理、产品、预算、数据、标准和资源；Case层验证这些能力能否对一个真实对象产生结果。只有Project层没有真实Case，项目容易变成文件建设。只有Case层没有Project控制，团队只能依赖个人临时协调。
Case是一个真实业务对象的完整交付记录。收到线索、简历、需求方向或演示数据都不足以单独构成有效Case。
四 启动前准备
1.  扫描现有材料。收集合同、会议记录、方案、系统、数据、历史交付和已有决策，标记来源与日期。
2.  建立事实分层。把已确认事实、原则共识、建议、假设、待核验任务、目标状态、未来范围和占位对象分开。
3.  确定唯一工作区。所有正式入口、主账、Readback、会议记录、证据和历史版本都放在同一受控目录中。
4.  确认角色和授权。先确认Owner、Principal、Case Manager或PM，再安排工作流和执行人。
5.  选择第一批真实对象。优先选择决策人可达、需求真实、证据可得、结果可观察且风险可控制的对象。
五 启动十个工作日
下面是通用默认节奏。复杂项目可以延长，但不得跳过责任签收和事实基线。日期变更应在Readback或Decision中一次写明，不得只口头延期。
启动完成的判断
D加十并不自动代表项目正常。只有当入口可读、范围已确认、责任人已Readback、主账能够反映真实状态、首个Gate通过且第一批真实对象已经建立，才可以把项目状态从启动中改为正常运行。
六 角色和责任
七 共同事实控制
共同事实不是一个大文件，而是一套优先级和更新纪律。静态基线定义当前可共同使用的事实；执行主账记录动态状态；Dashboard只呈现管理视图。三者冲突时，先查批准状态和证据，再通过Change Log或Decision修正，不允许在不同文件中各自改写。
事实状态
事实优先级
1.  已经批准且有证据的共同事实基线。
2.  正式Decision和签署文件。
3.  执行主账中的当前状态。
4.  Dashboard和周报中的汇报视图。
5.  会议纪要、即时消息、邮件和口头输入。
低优先级输入与高优先级事实冲突时，Case Manager应登记冲突、Owner、影响和建议处理，不能直接覆盖。
事实变更流程
1.  提交变化事实和证据。
2.  登记Fact ID、旧状态、新状态、影响对象和提出人。
3.  专业Owner确认专业事实，Principal确认项目影响。
4.  更新共同事实基线或Decision。
5.  同步主账、Dashboard、周报和相关Case。
6.  将被替代版本移入Archive并保留追溯。
八 任务拆解标准
项目按项目 工作流 工作包 Action Case Evidence六级拆解。Action是最小可管理任务，Case是最小真实结果单元，Evidence是支持状态和验收的记录。
可执行任务的最低字段
任务书的完整主线
对需要恢复、跨团队协作或存在争议的任务，负责人应按以下主线下达任务书。
九 Readback责任签收
Readback解决任务是否被真正理解和接受。已发送、已读、收到或群内回复好的，只能证明信息到达，不能证明对范围、交付和日期形成承诺。
Readback必须回答的内容
是否接受本人的角色和任务。
第一项交付物是什么。
承诺完成日期是什么。
实际执行自然人是谁。
依赖、资源和需要调整的事项是什么。
不能接受时的原因、替代方案和新日期是什么。
默认要求  责任人在任务发出后一个工作日内Readback。沉默不视为接受。Case Manager记录接收日期并将结果回写主账，Principal对拒绝、资源缺口和跨工作流冲突作出决定。

十 执行主账和Dashboard
执行主账是结构化事实源，至少包括Action、Workstream、RAID、Decision、Case和Evidence Index。Dashboard从主账生成，用于会议和管理层查看。Dashboard可以提供筛选和本地备注，但这些操作不能自动改变主账，除非项目已经实现并验证双向同步。
版本控制建议
保留一个永不覆盖的issued基线。
每周使用一个执行主账版本，周内在同一文件更新。
每次收到新交付或Readback后，在约定时限内回写并登记Change Log。
周五锁定主账，同步Dashboard，导出JSON或PDF快照并生成文件清单或hash。
下周建立新版本，旧版本移入Archive并标记由哪个版本替代。
入口文件和FILE INDEX必须始终指向同一个当前主账和Dashboard。
十一 Evidence和状态关闭
任务完成必须经过交付、证据、验收和回写。任何一项缺失，都只能处于已提交待验收或进行中状态。
Evidence等级
完成和关闭的验收链
1.  执行人提交交付物并说明完成范围和未完成范围。
2.  Case Manager登记Evidence ID、来源、版本和位置。
3.  验收人按事先约定的标准给出接受、返工或拒绝结论。
4.  专业事项由相应专业Owner复核，不由项目管理角色代替。
5.  主账状态、下一动作、Updated At和相关RAID同步更新。
6.  Dashboard和周报在下次刷新时与主账一致。
十二 Gate阶段验收
Gate控制的是是否具备进入下一阶段的条件，不是检查日期是否到达。项目可以按实际风险调整Gate名称，但必须保留进入条件、证据、验收人、结论和附带条件。
硬边界  上线、对外发布、使用真实个人数据、开展受规管活动、签约或收费，必须增加相应的法律、数据、安全、牌照、财务或授权Gate。项目日期不能代替这些批准。
十三 周度运行节奏
会议控制规则
会前从主账生成议题，不从聊天记录临时拼接。
会上只形成事实确认、Decision、Action或Evidence请求四类结果。
会后在约定时限内回写Owner、Due、依赖、结论和证据位置。
需要专业确认的内容标记待复核，不在会议中越权定论。
周报只汇报变化、结果、风险、决策请求和下一步，不重复整份主账。

十四 逾期和项目恢复
当项目出现大量逾期、Owner不清、状态互相矛盾或Dashboard失真时，应停止继续增加新任务，先恢复共同事实和交付闭环。恢复不是把所有Due向后移动，而是重新确认每项任务是否仍应存在、由谁承担、交付什么以及凭什么关闭。
恢复七步法
1.  冻结扩张。暂停新增非关键任务和未经批准的范围。
2.  建立恢复基线。锁定当前主账、Dashboard、事实基线和证据清单。
3.  逐项Disposition。将旧任务分为已完成待证据、阶段成果待拆分、重新激活、合并关闭、移出范围、待Owner和决策升级。
4.  实名Readback。向每个Owner发个人任务表，取得接受、调整或拒绝以及新Due。
5.  恢复关键路径。先处理P0、红灯、专业Gate和第一批真实Case。
6.  完成证据关闭。补交付、Evidence、验收和回写，不能用批量改状态恢复表面正常。
7.  账板对账。确保主账、Dashboard、周报和会议结论无矛盾，再由Principal确认恢复状态。
可以宣布恢复正常的标准
十五 项目负责人首月行动表
负责人每周需要回答的七个问题
1.  本周产生了哪些可验收结果，而不只是完成了哪些活动。
2.  哪些共同事实发生变化，谁确认，证据在哪里。
3.  第一批真实Case或验证对象走到什么阶段。
4.  哪些P0、红灯和专业Gate阻塞下一阶段。
5.  哪些责任人尚未Readback，哪些承诺已逾期。
6.  需要我作出的Decision、资源调整或范围取舍是什么。
7.  主账、Dashboard和周报是否使用同一个版本和状态。
