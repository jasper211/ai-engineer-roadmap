## 一、能力线说明

HKIA demo 只有一条线性流程，不像 PTA 那样有"被动执行+主动巡检"两条线——demo 阶段不做自动化/调度，就是"跑一次、从抓取到本地入库"。

## 二、L3 端到端流程

```
┌───────────┐    ┌───────────┐    ┌───────────┐    ┌───────────┐
│ L3-HKIA-01│ → │ L3-HKIA-02│ → │ L3-HKIA-03│ → │ L3-HKIA-04│
│ 报表发现   │    │ 文件抓取   │    │ 表格解析   │    │ 标准化落地 │
│ +真实链接  │    │ (Playwright)│  │ (双引擎)   │    │ (本地存储) │
└───────────┘    └───────────┘    └───────────┘    └───────────┘
```

四步而不是 SOP 模板默认的五步——"发现"和"抓取"因为都依赖同一个 Playwright 会话（打开年份页→拿真实 href→下载），拆成两个 skill 意义不大，但仍是两个逻辑清晰的输入输出单元，见下表；demo 阶段没有独立的"同步归档"步骤，人工核对（成功标准）直接查本地存储即可，不需要单独产出一份归档报告。

## 三、每个 L3 的输入输出

| L3 编码 | 名称 | 输入 | 输出 | 对应 skill/tool |
|---------|------|------|------|------|
| L3-HKIA-01 | 报表发现 | 硬编码的目标年份页 URL（`market_6_2023.html`/`market_6_2024.html`/`market_7_2023.html`/`market_7_2024.html`，demo 范围固定 2023Q1~2024Q2，不做全站爬取） | 报表清单（`period, business_type, file_url, file_ext`的列表，`file_ext`按真实探测结果记录，因为文件名模式不完全统一，不能靠拼接猜测） | `skills/report_discovery.py`（依赖 `tools/browser_fetcher.py`） |
| L3-HKIA-02 | 文件抓取 | L3-01 产出的报表清单 | 本地原始文件（按 `business_type/period` 分目录存放）+ 抓取时间戳 | `skills/report_discovery.py` 同一模块内的下载动作，或拆到 `tools/browser_fetcher.py` 的下载方法——两者算同一个 Playwright 会话内的连续动作 |
| L3-HKIA-03 | 表格解析 | 本地原始 Excel 文件 | 每期的原始字段表（category/metric/value 等，未翻译未标准化） | `skills/excel_parser.py`（内部按 `business_type` 分流：一般业务用 `openpyxl` 读 `.xlsx`，长期业务用 `xlrd` 读老版 `.xls`——两套解析逻辑不合并，见需求定义第七节风险表） |
| L3-HKIA-04 | 标准化落地 | L3-03 产出的原始字段表 | 长表格式数据写入本地存储：`date, category, metric_name, value, unit, source_report, fetched_at, period_type`（`period_type` 标注 YTD_Q1/YTD_H1/YTD_9M/YTD_FY，见需求定义第四节） | `skills/normalizer.py` + `memory/workspace.py`（本地存储读写） |

### 3.1 工具/技能职责边界

- `tools/browser_fetcher.py`：纯技术层，只负责"用 Playwright 打开一个 URL、返回渲染后的 DOM 或下载一个文件"，不知道 IA 官网页面结构，可被其他 skill 复用
- `skills/report_discovery.py`：知道 IA 官网页面结构（年份页里去找 `[EXCEL]` 链接文本对应的 `href`），业务专属逻辑
- `skills/excel_parser.py`：知道两类报表的表格内部结构差异，业务专属逻辑
- `skills/normalizer.py`：知道标准化长表的字段口径（含中文翻译、YTD 标注），业务专属逻辑
- `memory/workspace.py`：本地存储的读写封装 + HKIA 专属工作区隔离（不写入本项目仓库以外或其他 Agent 的目录）

### 3.2 遗留的真实未知项（留给 SOP 第4步开发阶段第一件事去实测，不在第2步流程设计里假装已经知道）

- 两类 Excel 文件内部真实的 sheet 名、表头层级、category/metric 字段的真实文案，需要开发阶段先人工打开一份 2023 Q1 的样本文件核实，再定 `excel_parser.py` 的具体解析规则——本流程设计只锁定"输入是 Excel 文件、输出是原始字段表"这个边界，不锁定内部字段名
- 是否所有 12 份文件（2023 年 4 期【Q1/H1/9M/FY】+ 2024 年 2 期【Q1/H1】，共 6 期 × 2 类报表 = 12 份 Excel）都能被 Playwright 稳定下载到，还是个别期数链接失效——开发阶段第一件事应该是先把 12 份文件的真实下载状态过一遍，而不是假设全部可用

## 四、本地存储选型建议（供第3步配置编写时定案）

建议 **SQLite**：demo 阶段数据量小（8 份报表），SQLite 比 CSV 更方便做"人工核对官网原始数字"时的查询（成功标准要求抽查3期），比 Parquet 更不需要额外依赖（Python 内建 `sqlite3`），且跟"后期迁移云端 PostgreSQL"的路径最接近（同为关系型，迁移时 schema 基本可以直接搬）。CSV 只作为验收阶段的导出物（方便 Jasper 拿去跟官网 Excel 逐行核对），不作为存储主形式。
