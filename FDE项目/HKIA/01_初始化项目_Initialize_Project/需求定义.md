## 一、这个 Agent 解决什么问题？

**现状痛点**：业务团队依赖人工从香港保险业监管局（IA）官网下载、整理长期业务季度保费统计报表，存在重复劳动，数据分散在多份 Excel 里不便查询对比。

**核心问题**（demo 范围）：把 IA 官网已发布的长期业务季度临时统计数字（2023 Q1 ~ 2026 Q1，共 13 期）解析、标准化、存入本地数据库，让这 13 期数据可以被统一查询、口径一致、可核对。自动化抓取本身推迟到下一版本。

## 二、谁用这个 Agent？

| 角色 | 使用方式 | 期望价值 |
|------|---------|---------|
| Jasper | 人工下载源文件放入指定目录，触发 Agent 解析入库 | 13 份分散 Excel 变成一张可查询的本地表 |
| 业务团队 | 查阅本地存储数据（或后续 Dashboard）做决策参考 | 数据口径统一可信 |
| （后续）PTA / AI 协同终端 | 可能的调度方，未来接入自动化抓取后触发 | 纳入统一任务调度 |

## 三、成功标准

**量化**：抽查 3 期数据，人工核对本地保存的数据与官网原始 Excel 数字一致（不允许静默丢字段/错行）。

**定性**：
- [ ] 13 份长期业务 Excel（2023Q1~2026Q1）解析、标准化为长表格式，存入本地数据库
- [ ] 数据保留原始口径标注（YTD 累计区间），避免不同期口径被错误合并
- [ ] `.xls`（2023~2024Q2）与 `.xlsx`（2024Q3起）两种文件格式都能正确解析，不因文件名不统一或格式切换而漏掉某一期

## 四、需求边界（demo 范围）

### 4.1 在范围内（Do）

- **长期业务**季度临时统计数字，**2023 Q1 ~ 2026 Q1，共 13 期**
- 数据来源：Jasper **人工下载** ia.org.hk 官网原始 Excel 文件，放入 `07_接入记忆_Integrate_Memory/raw_data/`（见该目录 README 的 13 个期待文件名）——demo 从"解析本地文件"开始，不做自动抓取
- 解析两种真实存在的 Excel 格式：`.xls`（老版，2023~2024Q2，需要 `xlrd`）+ `.xlsx`（新版，2024Q3起，需要 `openpyxl`）
- 标准化为长表格式：`date, category, metric_name, value, unit, source_report, fetched_at, period_type`（`period_type` 标注 YTD_Q1/YTD_H1/YTD_9M/YTD_FY）
- 存储：本地 SQLite
- 一次性全量解析即可，不需要增量去重逻辑

### 4.2 不在范围内（Don't，留作后续批次）

- **一般业务**——实测确认它在 2024 Q3 之后真的断更了（页面只剩期间文字，无下载文件），跟长期业务不是同一种情况，本次 demo 不做
- **自动化抓取**（Playwright 或其他方式）——沙盒环境测试 Cloudflare 行为不稳定、无法决定性验证，这次直接用人工下载替代，自动化留到下一版本单独验证
- 增量抓取/去重逻辑、定时调度（demo 验证通过后再设计）
- 持牌中介人数目统计、偿付能力等专项统计报表（启动方案第二/三阶段）
- 分析层：同环比计算、Claude API 自动摘要、异常提示（启动方案 Sprint 2）
- 前端 Dashboard 展示（启动方案 Sprint 3）
- 云端部署（本地优先，云端服务器是后期规划）

## 七、真实实测发现（Browser 实测，非猜测）

**导航路径**：官网首页 → 資源中心 → 市場及行業統計數據 → 長期業務季度發表的臨時統計數字（`quarterly_release_of_provisional_statistics_for_long_term_business.html` → `market_7_{year}.html`）

**13 份文件的真实命名**（文件名不统一是官网真实情况，不是下载错误——完整清单见 `raw_data/README.md`）：

| 年份 | 期数 | 格式 |
|---|---|---|
| 2023 | Q1~Q4 全部 4 期 | `.xls`（老版），如 `1q23long.xls` |
| 2024 | Q1~Q2 | `.xls` |
| 2024 | Q3 | `.xlsx`（新版，文件名 `3q24_long.xlsx` 多了下划线） |
| 2024 | Q4 | `.xlsx`（`4q24long.xlsx`，这次没有下划线） |
| 2025 | Q1~Q4 全部 4 期 | `.xlsx` |
| 2026 | Q1 | `.xlsx`（`1q26_long.xlsx`，又带下划线） |

**一般业务 vs 长期业务的真实差异（重要纠正）**：最初实测时只查了一般业务的 2025 年页面（确认无下载文件）就推断"两类报表都在 2024Q3 断更"，这个推断是错的——后来专门核实长期业务的 2024/2025/2026 年页面，发现**长期业务从未断更**，2024Q3 起只是文件格式从 `.xls` 换成 `.xlsx`（跟"風險為本資本制度（RBC）於2024年7月實施"的时间点吻合，但只影响文件格式，不影响长期业务报表本身是否继续发布）。一般业务确实断更（2024Q3起页面只剩期间文字，无下载链接），两者不能一概而论。

**每期数据是"年初至今累计值"**：页面期间是"一月至三月/一月至六月/一月至九月/一月至十二月"，即 Q1/H1/9M/FY 累计口径，不是独立单季度值，标准化层必须标注 `period_type`，否则环比会算错。

**Cloudflare 防护**：官网有 Cloudflare JS 挑战，纯 `requests`/`curl` 拿不到数据；自动化浏览器（含本次测试用的沙盒 Browser 工具）在文件下载这一步测试结果不稳定（时而403、时而通过），本版本 demo 直接用人工下载规避这个问题，不代表问题已解决——下一版本要做自动化抓取时，仍需要在真实本机环境跑决定性测试。

**robots.txt**：`User-agent: * / Allow: /tc/*`（仅 `/tc/datagovhk/*` 等少数路径禁止），目标报表路径不在禁止范围内。

**曾考虑过 data.gov.hk 分表CSV作为数据源**（同一份数据的中文分表版本，见 `data.gov.hk/tc-data/dataset/ia-ialtb-lstatsq2023q2`），因为它比 Excel 更好解析；但既然改为人工下载，直接拿 ia.org.hk 原始 Excel 更符合 Jasper 已经在操作的路径，data.gov.hk 这个选项先记录在案，不是本版本采用的方案。

## 八、风险与假设

| 风险 | 影响 | 应对 |
|------|------|------|
| 文件格式跨期不统一（`.xls` → `.xlsx`，文件名下划线时有时无） | 通用解析器容易漏判某一期 | 按真实文件名/扩展名分流解析，不假设统一模式；每期都要有明确的成功/失败信号 |
| 统计口径变化（YTD累计值、是否含相连长期业务/退休计划业务） | 历史数据被错误合并、环比算错 | 标准化层保留原始口径标注字段（`period_type`） |
| 人工下载可能漏下载或下错期数 | 数据不完整但不易发现 | 解析脚本对照 13 期清单做完整性校验，缺哪期要报出来，不能静默跳过 |
| 未来做自动化抓取时 Cloudflare 行为仍不确定 | 下一版本的采集层设计风险 | 留到下一版本单独用真实本机 Playwright 脚本验证，不在本次 demo 里假装已解决 |
