## 一、这个 Agent 解决什么问题？

**现状痛点**：业务团队依赖人工从香港保险业监管局（IA）官网下载、整理季度/年度保费统计报表，存在重复劳动，"数据发布 → 业务可用"周期长，且缺少趋势解读与异常提示。

**核心问题**：如何自动完成"抓取 → 标准化 → 存储"全链路，让 IA 官网发布新一期报表后，业务团队无需人工下载即可查到标准化数据。

## 二、谁用这个 Agent？

| 角色 | 使用方式 | 期望价值 |
|------|---------|---------|
| Jasper | 触发/维护 Agent，Sprint 0 技术选型确认人 | 减少人工整理报表的重复劳动 |
| 业务团队 | 查阅存储层数据（或后续 Dashboard）做决策参考 | 数据更新更及时、口径统一可信 |
| （后续）PTA / AI 协同终端 | 可能的调度方，触发 HKIA 抓取任务 | 纳入统一任务调度，而非独立 cron |

## 三、成功标准

**量化**：抽查 3 期报表数据，人工核对本地保存的数据与官网原始数字一致（不允许静默丢字段/错行）。

**定性（demo 范围）**：
- [ ] 一次性抓取 2023 年初至今的季度保费统计（中文页面），标准化为长表格式并保存到本地
- [ ] 数据保留原始口径标注，避免不同期口径被错误合并
- [ ] （demo 阶段不要求）自动化增量更新/去重——这是 demo 验证通过后的下一版本目标，本版本只求"跑一次、数出对"

## 四、需求边界（demo，第一阶段）

> v0.1.1 收窄（2026-07-29，Jasper 确认）：MVP 进一步收窄为"跑一次 demo 看效果"，不是"跑通可持续运行的链路"。自动化、增量、云端、双语都推迟到 demo 验证通过之后再设计。

### 4.1 在范围内（Do）

- 季度保费统计（一般业务 + 长期业务）抓取：Excel 附件（一般业务 `.xlsx`、长期业务老版 `.xls`）+ 对应 PDF，源页面语言不限（中/英文均可抓取）
- 标准化为长表格式：`date, category, metric_name, value, unit, source_report, fetched_at`，另加一个**累计区间标注字段**（如 `period_type=YTD_Q1/YTD_H1/YTD_9M/YTD_FY`），因为源数据是年初至今累计值，不是独立单季度值
- 时间范围：**2023 Q1 ~ 2024 Q2**（实测确认的唯一干净结构化数据窗口，不做全周期历史回溯）
- 采集方式：**Playwright**（真实浏览器自动化，能通过官网 Cloudflare 的 JS 挑战；不是 requests+BeautifulSoup，那个方案对这个真实站点跑不通）
- 存储：**保存到本地**（具体本地形式——SQLite / CSV / Parquet——第2步流程设计时确定；后期再设计云端服务器迁移）
- 一次性全量抓取即可，不需要增量去重逻辑——demo 阶段目标是"跑一次、产出正确"，不是"可重复运行不重复入库"
- **语言**：抓取源不限中英文；若源数据是英文（字段名/类别名），标准化层需要把 `category`/`metric_name` 等展示用字段翻译成中文——**最终呈现只看中文**，这是 Jasper 明确要求的，不是"顺手做双语"

### 4.2 不在范围内（Don't，按风险递增分批，不在本阶段做）

- 双语呈现（最终展示统一用中文，不需要中英文并列）
- 2023 年之前的全周期历史数据回溯
- **2024 Q3 至今**的数据——这段官网只有年度新闻稿+PDF附件（叙述性文字，非结构化表），结构完全不同于 2023Q1~2024Q2 的 Excel 表，风险更高，留作下一批单独处理
- 增量抓取/去重逻辑、定时调度、自动化触发（demo 验证通过后再设计）
- 持牌中介人数目统计、偿付能力等专项统计报表（启动方案第二/三阶段）
- 分析层：同环比计算、Claude API 自动摘要、异常提示（启动方案 Sprint 2）
- 前端 Dashboard 展示（启动方案 Sprint 3）
- 云端部署（本地优先，云端服务器是后期规划）

> 原因：启动方案本身建议"先做 MVP 把链路跑通，再横向扩展"；Jasper 进一步明确第一版只要"看个 demo"，不需要一步到位做成可持续运行的系统，避免过早为"自动化/云端/双语"设计返工。

## 五、L3 流程边界

- **起点**：IA 官网一般/长期业务季度保费统计页面（`market_6_{year}.html` / `market_7_{year}.html` 下的 Excel 附件，中/英文源均可），时间范围 2023 Q1 ~ 2024 Q2
- **终点**：标准化后的长表数据保存至本地，展示字段统一翻译为中文（存储形式待第2步确定）
- **不含**：分析层（同环比/LLM摘要）、前端展示、增量去重与调度自动化、云端存储——这些留到 HKIA 后续版本，届时再补充新的 L3 流程或独立能力线，不在本次流程设计里预先占位

## 六、待确认事项

**已确认（2026-07-29，Jasper）**：
- ✅ 语言：最终展示统一用中文；源数据中/英文均可抓取，若为英文需翻译展示字段（不是"只抓中文页面"）
- ✅ 时间范围：2023 年初至今，不做全周期历史回溯，第一版不设计自动化
- ✅ 存储：本地（后期再设计云端服务器）
- ✅ 技术栈落地环境：本地

**已用真实页面核实（2026-07-29，Browser 实测，非猜测）**：

导航路径：官网首页 → 資源中心 → 市場及行業統計數據 → 下列两个子项，与启动方案说的"季度保费统计"完全对应：

| 报表 | 入口页 | 年份页命名 | 文件命名（真实取样） |
|---|---|---|---|
| 一般業務季度發表的臨時統計數字 | `.../statistics/quarterly_release_of_provisional_statistics_for_general_business.html` | `market_6_{year}.html` | `files/1q23gen.xlsx`（新版 Excel） |
| 長期業務季度發表的臨時統計數字 | `.../statistics/quarterly_release_of_provisional_statistics_for_long_term_business.html` | `market_7_{year}.html` | `files/1q23long.xls`（老版 Excel，非 xlsx） |

**真实数据比合成数据脏，实测已经踩到 3 个坑**（对齐 SOP 5.2 第5条原则，提前记录，避免第4步才发现返工）：

1. **文件命名不统一**：长期业务 2023 Q3 的 PDF 叫 `3q23_long.pdf`（多一个下划线），其余期是 `Nq23long.pdf`；一般业务是 `.xlsx`，长期业务是老版 `.xls`——两类报表不能共用一个下载器，必须分别处理文件名模式和 Excel 引擎（`.xls` 需要 `xlrd`，`.xlsx` 需要 `openpyxl`）。
2. **每期数据是"年初至今累计值"，不是独立单季度值**：页面上的期间是"一月至三月/一月至六月/一月至九月/一月至十二月"，即 Q1/H1/9M/FY 累计口径。标准化层必须把这个"累计 vs 单季"的口径标注进字段，不能直接当独立季度值用，否则环比/同比会算错（这个字段设计本版本demo也要做对，即使分析层不在本阶段范围）。
3. **⚠️ 2024年7月起，这两个"季度保费统计"报表实质上断更了**：2024 Q1/Q2 仍有旧格式 Excel 文件，但 **2024 Q3 起到 2025 全年，页面上只列期间文字、没有任何 [PDF][EXCEL] 下载链接**。原因是官网说明"風險為本資本制度（RBC）於2024年7月實施，獲授權保險公司需要遞交新版本的監管申報表"。取而代之的是**每年一次的新闻稿 + PDF附件**（如 2026-04-24 发布的"2025年臨時統計數字"，附件 `files/2025_Provisional_Statistics_Annex.pdf`）——是叙述性文字夹杂数字，不是结构化 Excel 季度表。另外确认了一个相邻但不同的报表"保險業季度發表的臨時財務資料"（`Quarterly_Release_of_Provisional_Fin_Info_on_Insurance_Industry.html`）在 2024Q4 之后仍按季度更新到 2026 Q1，但那是资产负债类财务资料，不是保费统计，口径不同不能替代。

4. **⚠️ 官网有 Cloudflare 机器人防护，纯 `requests`/`curl` 拿不到数据**：直接用 curl 请求任意页面（包括 `robots.txt`）都会先返回一个 "Just a moment..." 的 JS 挑战页，不会返回真实内容；用带 JS 渲染的浏览器（本次用 Claude Browser 工具核实）能正常自动通过。这意味着启动方案里"Python：requests + BeautifulSoup"的采集层技术选型在真实站点上跑不通，**需要换成会真正执行 JS 的浏览器自动化方案（如 Playwright），而不是任何专门用来"破解/绕过"验证的手段**——这是我作为助手在任何情况下都不会做的事，所以选型上直接换轨到"用真实浏览器访问公开政府数据"这条正规路径，不去尝试规避检测。

**robots.txt 确认结果**：`User-agent: * / Allow: /tc/*`（仅 `/tc/datagovhk/*` 等少数路径禁止），目标报表路径不在禁止范围内；文件本身也在 Cloudflare 挑战之后，无显式 crawl-delay 声明。

**已确认（2026-07-29，Jasper）**：
- ✅ demo 时间窗口收窄为 **2023 Q1 ~ 2024 Q2**（唯一有干净结构化 Excel 数据的窗口）；2024 Q3 起至今的年度新闻稿+PDF附件作为风险更高的下一批，不在本次 demo 范围
- ✅ 采集层技术选型从 `requests + BeautifulSoup` 改为 **Playwright**（真实浏览器自动化，能通过 Cloudflare 的 JS 挑战；不是任何绕过检测的手段）

## 七、风险与假设

| 风险 | 影响 | 应对 |
|------|------|------|
| 报表格式不统一（一般业务 xlsx vs 长期业务老版 xls，文件名下划线不一致） | 通用解析器容易两头不讨好 | 按报表类型分别写 parser 和文件名匹配规则，不做万能解析器 |
| 官网改版导致抓取脚本失效（已实测：2024Q3起旧格式报表断更） | 静默失败、数据断档 | 抓取失败/找不到下载链接需要可感知的信号，不能静默吞错误；demo 只覆盖有结构化数据的窗口 |
| 统计口径变化（年初至今累计值、是否含相连长期业务/退休计划业务） | 历史数据被错误合并、环比算错 | 标准化层保留原始口径标注字段（含"累计区间"字段） |
| Cloudflare JS 挑战拦截非浏览器请求 | 简单 HTTP 库拿不到数据 | 采集层用 Playwright 等浏览器自动化，不用规避检测类手段 |
